# M85 · Contract / Bootstrap · этап 1 декомпозиции

Основа: диагностический архив 2026-10-14 08:43 (M83) + хотфикс M84. Цель — отделить запуск игровых сервисов от игрового поведения, а чтение Asset Manager — от HTTP-процедур и баз данных. Это **первый этап**, не полная декомпозиция всех монолитов.

## Серверное владение

- `bootstrap/ServiceCatalog.luau`: единственный список сервисов, их порядок, lazy require, обязательность и зависимости. В игровую логику не вмешивается.
- `bootstrap/ServiceBootstrap.luau`: однократная последовательная инициализация, проверка целостности графа, изоляция ошибок через `pcall`, статус `ready | failed | blocked`, снимок состояния. Никаких Remote или управления NPC.
- `init.server.luau`: только composition root и серверные атрибуты готовности. Атрибуты служебные (не публикуются клиентам).

Система не начинает зависимый сервис, если prerequisite не перешёл в `ready`; остальные независимые сервисы продолжают запускаться. `critical` влияет на `CoreServicesReady`, а не на запуск независимых инструментов. `NpcSpawnerService` и `MonsterSpawnerService` выделены как потенциально деградирующие домены; сбой NPC не блокирует Studio-only debug remote. `MonsterAIService` зависит от успешного запуска спавнера.

**Границы гарантии:** асинхронные ошибки уже запущенных задач не отслеживаются bootstrap автоматически. Он фиксирует только ошибки `require` и синхронной `Start()`. Если `Start()` успел создать часть объектов, bootstrap пока не может откатить эти побочные эффекты — следующий этап lifecycle/cleanup.

## Host Agent: read-only API

- `api/read_catalog.py` — чтение реестров Character/NPC/Monster/Weapon/Animation и истории публикаций.
- `api/read_world.py` — чтение спавнов, Location Assets, настроек и timeline-сессий.
- `api/read_dispatch.py` — лёгкий HTTP-независимый выбор read-only маршрута.
- `host_agent.py` — адаптер `BaseHTTPRequestHandler`/аутентификация/сериализация и composition root с явно переданными зависимостями.

Сохранены существующие URL, заголовок `X-Control-Token`, ответы GET 200/400/401/404 и старые POST/DELETE без изменений. Форматы опубликованных реестров и именование NPC не мигрируют. POST/DELETE будут выноситься по доменам **отдельным этапом** с тестами записи/удаления/публикации на временной базе и проверкой side effects Studio Bridge.

## Регрессионные проверки

- `verify.py` — прежние контрактные проверки по новым файловым границам.
- `test_http_read_contracts_m85.py` — настоящие HTTP-запросы к текущему Handler с fake application services: GET всех категорий, publication, фильтры, авторизация, 404, 400 и контроль двух существующих POST/DELETE.
- `test_server_bootstrap_contracts_m85.py` — каталог зависимостей и защита от возврата монолитной инициализации; **не исполняет Luau в движке**.
- `unittest discover` — регрессия предыдущих M-патчей.

Требуется ручной Studio Play smoke: вывод статуса готовности на `Game1Server` (`CoreServicesReady=true` и `Service_* = ready`), наличие debug remotes, Spawn/Combat/Hit/Return как до M85. Отдельно воспроизвести ошибку при старте NPC в тестовой копии, убедиться, что debug-remote появились; не вносить искусственный отказ в основной проект.
