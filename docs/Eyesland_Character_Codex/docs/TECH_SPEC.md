# EYESLAND — техническое задание на базового персонажа, риг и систему сменных мешей

**ID:** EYESLAND-CHARACTER-BASE-001  
**Версия:** 1.0 · 26 октября 2026  
**Исполнитель:** Codex через Blender MCP + Python API (`bpy`)  
**Этап:** первая производственная версия базовой модели; не полноценная система MMORPG и не библиотека готовых комплектов  
**Язык исходников:** английские стабильные идентификаторы; документация на русском.

## 0. Короткое описание результата

СОЗДАТЬ, а не только описать, в Blender полноценную, визуально аккуратную и готовую к дальнейшей работе **единую нейтральную модель персонажа Eyesland**: лысая цельная голова, стройное низкополигональное тело, строго симметричные части тела, собственный скелет, вручную доведённый skinning, базовые поверхности и UV, независимые крепления оружия/щита/плаща/наплечников/волос, а также механически проверяемые стыки сменных деталей.

Базовое правило: **один персонаж → один неизменяемый контракт скелета → много независимо подменяемых частей тела**. Одинаковая форма и UV → можно заменить текстуру. Отличается силуэт → заменить skinned mesh соответствующей области. Тело под закрытой частью не должно одновременно рендериться. Для сменной детали не создаётся новая копия игрового скелета.

**Это полностью кастомный игровой персонаж. Не адаптировать его к Roblox R6/R15, стандартным аватарам, Rthro, HumanoidDescription, layered clothing и marketplace-ограничениям.** При этом сохранять реальную совместимость с импортом кастомного skinned rig в Roblox. Ограничения формата экспорта и импортёра проверять экспериментально, а не обходить сомнительными конструкциями.

### Строгие художественные требования
- Силуэт пропорционально уже стандартного «квадратного» Roblox-персонажа, но **не** взрослый реалистичный человек: умеренная стилизация и слегка увеличенная голова.
- Один и тот же корпус подходит для всех полов: никакой груди, гендерно выраженных таза/плеч, специализированных форм туловища. Отличия пола позже — лицо, волосы, одежда.
- Торс, руки, ноги, кисти — простые объёмы, но не механический набор прямоугольных Roblox-блоков. Сохранять округлённые/скошенные углы и чистые low-poly плоскости.
- Минимальная анатомия, пригодная для быстрого построения одежды; аккуратные локти, колени, лодыжки и запястья.
- Не создавать отдельную «женскую» или «мужскую» геометрию.
- Без волос, бород, украшений, боевой брони, плаща, щита или оружия в финальном игровом базовом меше; только **временные тестовые муляжи** в скрытой служебной коллекции.
- Лицо: плоская/слегка выпуклая фронтальная поверхность головы с подготовленными UV для будущей текстуры глаз/точек/рта. Реалистичные глаза, ресницы, зубы не моделировать. Лицевую анимацию и blendshapes не делать. Позднее Eyesland может использовать светящиеся точки вместо глаз; не встраивать их в геометрию.
- Готовая базовая внешность для предпросмотра может напоминать светлую тунику + тёмные штаны/простые сапоги с референса, но это должна быть **базовая сменная поверхность**, а не несъёмные пояс, наплечники или накладные украшения. Полностью лысая базовая голова должна выглядеть законченно и без причёски.

## 2. Координатный контракт (НЕ изменять после утверждения)

| Правило | Значение |
|---|---|
| Blender | объект `ARM_EYESLAND` в world origin (0,0,0); source units — метры, Unit Scale=1 |
| Ось персонажа | Z вверх, X влево/вправо, **лицом к -Y** |
| Зеркало | плоскость X=0; суффикс `.L` = **левая сторона персонажа**, X>0; `.R` = правая, X<0 |
| Rest pose | симметричная A-pose: руки на 20–30° от туловища, ладони ориентированы на простой захват, стопы параллельны |
| Ориентация и нейтраль | pelvis/head строго по оси X=0; персонаж без поворотов в rest; без характерных наклонов |
| Размер | исходный ориентир высоты H≈1.70 м в Blender, масштаб всего персонажа согласованный; **не** подгонять частями |
| Пропорции | приблизительно 5–5.5 высот головы; ширина плеч около 1.4–1.6 ширины головы; не измерять пиксели концепта как эталон физической анатомии |
| Transform | mesh-object/armature object transform: location=(0,0,0) для root/asset-координат, rotation=(0,0,0), scale=(1,1,1); geometry в локальных координатах |
| Export | в файлах записи чётко обозначать реальную конверсию осей и масштаба в зависимости от выбранного формата; не смешивать source/world/bind space |

Голова, туловище и таз — центрированы; все лево-правые пары отражены строго. Не делать handed mirroring с **отрицательным объектным scale** на экспортируемых мешах — применить отражение и нормали на этапе моделирования.

## 3. Обязательные 15 базовых заменяемых мешей

**Это отдельные mesh objects, а не одна сетка с материалами и не rigid blocks.** Они используют общую армaтуру `ARM_EYESLAND`, соответствующие костям vertex groups и модификатор Armature.

| Mesh ID | Область | Skin weights / ожидаемые влияния |
|---|---|---|
| `B_HEAD` | цельная лысая голова с ушами, лицом и гладким черепом, без отдельных «лоб/затылок/скальп» | `head`, при нужде `neck` |
| `B_TORSO` | грудная клетка, живот, верх спины, плечевой переход/шея до области стыка | `spine_01`,`spine_02`,`neck`,`clavicle.*` по необходимости |
| `B_HIPS` | таз и нейтральный промежностный объём, без интимной детализации | `pelvis`,`spine_01`,`thigh.*` |
| `B_UPPER_ARM.L`, `.R` | от плечевого сустава до зоны локтя | `clavicle.*`,`upper_arm.*`,`forearm.*` |
| `B_FOREARM.L`, `.R` | от локтя до запястья | `upper_arm.*`,`forearm.*`,`hand.*` |
| `B_HAND.L`, `.R` | упрощённая кисть с читаемым большим пальцем; **без рига отдельных фаланг** | `hand.*` |
| `B_THIGH.L`, `.R` | бедро | `pelvis`,`thigh.*`,`shin.*` |
| `B_SHIN.L`, `.R` | голень | `thigh.*`,`shin.*`,`foot.*` |
| `B_FOOT.L`, `.R` | стопа, простая форма ботинка/ноги | `foot.*`, при необходимости `toe.*` |

Итого: 3 центральных + 12 парных = **15 независимых базовых объектов**.

**Тело не нарезать по каждой грани материала.** Фактический заменяемый «сектор» — перечисленный mesh. Художник может заменить сразу несколько секторов одним предметом экипировки, не создавая неуправляемый список уникальных частей для каждого комплекта.

### Две границы: mesh partition и equipment slot
- `mesh region` — физическая область: `B_TORSO`, `B_FOREARM.L`, и т. д.
- `equipment slot` — предмет: `CHEST`, `LEGS`, `GLOVES`, `BOOTS`, `SHOULDERS`, `CAPE`, `HEADGEAR`, `WEAPON.L/R`, `SHIELD.L/R`, `HAIR`.
- Один предмет может **заменить несколько mesh regions**. Пример: нагрудник с длинными рукавами заменяет `B_TORSO`+оба `B_UPPER_ARM`; высокие латные сапоги — `B_SHIN.L/R`+`B_FOOT.L/R`.
- Никакой зависимости «один предмет = строго один MeshPart»; важно явное описание областей, масок и совместимости.

## 4. Скелет: один авторитетный Armature

Создать `ARM_EYESLAND` с именами ниже. У каждой кости должно быть уникальное имя. Нужен **деформирующий скелет** без обязательной зависимости от Rigify/R15. Дополнительные control bones для Blender возможны в отдельной коллекции и не должны попадать в игровой экспорт, ломать именование или изменять контракт ниже.

### 4.1. Иерархия и имена (обязательные)

```
root                         [NON_DEFORM, world/ground anchor]
└─ pelvis                    [DEFORM]
   ├─ spine_01               [DEFORM]
   │  └─ spine_02            [DEFORM]
   │     ├─ neck             [DEFORM]
   │     │  └─ head          [DEFORM]
   │     │     └─ hair_mount [NON_DEFORM; будущие цельные причёски]
   │     ├─ clavicle.L       [DEFORM]
   │     │  └─ upper_arm.L   [DEFORM]
   │     │     ├─ forearm.L  [DEFORM]

   │     │     │  │  └─ weapon_grip.L  [NON_DEFORM]
   │     │     │  └─ shield_mount.L    [NON_DEFORM]
   │     │     └─ shoulder_mount.L    [NON_DEFORM]
   │     ├─ clavicle.R       [DEFORM]
   │     │  └─ upper_arm.R   [DEFORM]
   │     │     ├─ forearm.R  [DEFORM]

   │     │     │  │  └─ weapon_grip.R  [NON_DEFORM]
   │     │     │  └─ shield_mount.R    [NON_DEFORM]
   │     │     └─ shoulder_mount.R    [NON_DEFORM]
   │     ├─ cape_mount       [NON_DEFORM, верх спины у воротника]
   │     │  ├─ cape_clasp.L  [NON_DEFORM, верхний левый угол плаща]
   │     │  └─ cape_clasp.R  [NON_DEFORM, верхний правый угол плаща]
```

`root` должен быть центрирован в (0,0,0), **без skin weights**. За движение/центр тела отвечает `pelvis`, а не случайная кость оружия. `spine_02` — грудная зона для поворота верхней части тела. Никаких имен вроде `Bone.001`, дублирующих скелетов или автоматических суффиксов у производственных объектов. Все socket bones имеют `use_deform=False`.

### 4.2. Щит: особое обязательное требование

`weapon_grip.L/R` и `shield_mount.L/R` — **четыре отдельные кости**, отдельные локальные трансформы, независимые места крепления. Не объединять их и НЕ крепить щит в `weapon_grip`. Защитный щит фиксируется рядом с наружной/тыльной стороной предплечья, чуть ближе к запястью, чтобы он повторял движение предплечья во время защиты.

- **Модель для Eyesland:** `shield_mount.L` дочерняя `forearm.L`; `shield_mount.R` зеркальная дочерняя `forearm.R`.
- Позиция: щит виден снаружи предплечья, перекрывает его часть при блоке, кисть может находиться возле ремня/рукоятки щита; без требуемого mesh-слияния со стопой/hand.
- Оси каждого сокета: выбрать и документировать единую локальную систему: локальная +Y (или другое выбранное направление, но одинаковое в зеркальном контракте) задаёт *внешнюю нормаль лицевой поверхности щита*, а локальная +Z — *верх щита*. Поскольку зеркальное отражение координат меняет handedness, **не использовать отрицательные матрицы scale для левого/правого asset**: получить proper-rotation со стандартизированным facing через явные ориентации sockets; проверить на симметричных тестовых муляжах и сохранить `attachment_local_frames.json`.
- Кость щита на любой стороне существует всегда, даже если в инвентаре щита нет. Руки доступны для собственных оружейных сокетов независимо. **Боевая совместимость** (например, щит исключает определённый двуручный стиль или оружие в левой руке) — задача игровой логики в будущем, не геометрической архитектуры.
- Создать 2 простых временных щита-маркера (не финальные щиты) и 2 временных оружия-маркера для проверки креплений. Проверить `weapon_grip.R` + `shield_mount.L`, затем зеркальный случай `weapon_grip.L` + `shield_mount.R`.

**Lineage II:** публичные L2J-подобные исходники показывают эквип-слот `L_HAND` для левых предметов, включая щит; это серверная/инвентарная логика. Достоверно извлечённого оригинального имени кости, `socket` или exact bind matrix клиента Lineage II здесь нет. **Не заявлять**, что оригинальная Lineage II использовала именно `forearm` как bone; выбрать этот конструктивный вариант для наших нужд. Отсылку к L2 понимать как визуальную механику ношения щита и раздельные слоты, не как попытку скопировать чужие файлы.

### 4.3. Наплечники
- `shoulder_mount.L/R` — по одному независимому симметричному сокету, дочерние соответствующим `upper_arm.L/R`.
- Место под будущий отдельный rigid или skinned меш наплечника. Не моделировать постоянные наплечники в базовом персонаже.
- Проверить, что при подъёме руки до ~90–120° сокет остаётся над верхней частью плеча, не мигрирует в корпус и даёт возможность подобрать безопасную форму наплечника. Допустим отдельный shoulder rig для сложных наплечников позже, сейчас не нужен.
- Не путать декоративное наплечное оснащение с `B_UPPER_ARM` или `B_TORSO`.

### 4.4. Плащ
- `cape_mount`: центральный узел у воротника сзади, родитель `spine_02`.
- `cape_clasp.L/R`: симметричные дополнительные узлы у плечевой линии, дочерние `cape_mount`.
- **Базовое тело НЕ содержит меш плаща.** Слоты лишь готовят будущий независимый плащ: он может быть rigid, отдельным skinned mesh с дополнительной физикой/костями либо анимированным — без изменения базового рига. План физики и костей хвоста плаща не проектировать сейчас.
- Временно привязать тестовую плоскость-полоску с объёмом к центральному mount и проверить, что она следует наклону туловища, а не костям рук или голове.

### 4.5. Волосы
- Только `hair_mount` — дочерняя `head` для одной цельной съёмной причёски и будущего шлема/головных уборов.
- Не делать волосы/скальп/чёлку/хвост сейчас. Не разрезать голову на части ради волос.
- Позже цельный hair mesh крепится к `hair_mount` как жёсткий объект; при необходимости отдельная причёска сможет иметь свои вторичные кости/пружины независимо от `ARM_EYESLAND`.
- Лицо — UV/материал головы, никаких костей для глаз или facial rig на этом этапе.

## 5. Skinning и геометрия суставов

1. `B_*` должны использовать **один общий rest pose**, одну иерархию bones, идентичные названия/позиции узлов. У модульной брони могут быть иная топология и количество вершин, но соответствие к скелету — строго то же.
2. Каждая деформируемая вершина имеет нормализованные веса, сумма≈1; максимум **4 bone influences per vertex** для надёжного импорта; `root` и все `*_mount`/`weapon_grip` не деформируют тело.
3. Сначала автоматический baseline weight допустим только как начальная гипотеза. **Обязательно ручная/скриптовая корректировка** локтей, коленей, плеч, паха/таза, запястий, шеи, стыков мешей.
4. Контролировать folded deformation: local bones rotation, weight gradient, оставлять достаточные петли сетки у суставов; не делать жёсткое «ломание палки» и не раздувать цилиндры.
5. На парных частях weights точны зеркально, с заменой `.L↔.R`. Проверить математически, а не на глаз.
6. Не создавать IK bones в игровом skeleton contract, если они не нужны для этого этапа. Если для удобства используется Blender control rig/IK, экспортный `ARM_EYESLAND` должен оставаться самодостаточным и baking должен сохранять нужные deform bone transforms.
7. Повороты и joint origins: плечо анатомически под верхним сегментом торса, локоть в месте сгиба, запястье в центре кисти, тазобедренный в центре бедра, колено на линии сгиба, лодыжка у сгиба стопы; контролировать пропорции по референсу.
8. Все нормали наружу; закрытые меши не должны иметь видимых backface дыр. Квады в исходнике где разумно, триангуляция контролируемая для экспорта. Не использовать bevel/subdivision так, чтобы потерялся low-poly стиль.

### 5.1. Стыки мешей — ключевая зона качества

Отдельные меши, которые сгибаются, без специального протокола могут разойтись, породить дырки, просвечивание и неправильную форму. Применить **гибрид «совместимые кольца + скрытый заход/манжета»**:

- Для каждой пары соседних областей определить canonical seam profile: положение границы в bind pose, число опорных вершин/радиус, bone weight profile и ориентацию нормалей.
- На **видимой** границе соседних вариантов соблюдать совместимость профиля (не обязательно совпадение topology за пределами seam). Соответствующие вершины имеют согласованные веса, чтобы при движении тела шов оставался замкнутым.
- Дополнительно сделать **невидимое внутреннее перекрытие/закрытый торец** под манжетой для аварийной защиты от щелей. Не накладывать две наружные копланарные поверхности (z-fighting).
- Торцевые закрытия (caps) должны быть внутри объёма либо закрыты одеждой; наружу через локоть/колено они не должны виднеться.
- Модельные границы по возможности прятать там, где в будущем обычно будут воротник, пояс, перчаточная/обувная манжета, сгиб ткани: шея, верх плеча, локоть, запястье, талия, пах/верх бедра, колено, лодыжка.
- При отсутствующей внешней экипировке base mesh возвращается и полностью закрывает тело — никаких дыр при смене комплектов.
- Не склеивать разные `B_*` в один production меш ради «лечения» швов.
- Для дополнительной одежды из широких деталей допускается перекрыть шов единым item mesh; такой предмет в конфиге должен **скрыть обе базовые области**.

### 5.2. Единый seam/compatibility contract

Построить в `contract/seams.json` или аналогичном data-файле список соседних регионов и контрольных rings/points. Минимальный перечень: голова↔торс(шея), торс↔таз(талия), торс↔верхние руки(плечи), верхняя рука↔предплечье(локоть), предплечье↔кисть(запястье), таз↔бедро, бедро↔голень(колено), голень↔стопа(лодыжка). У каждого шва сохранять зеркальный эквивалент.

**Запрещено:** произвольное продвижение seam positions в новой броне. Любая новая форма должна соблюдать те же точки стыков, даже если внешний силуэт за пределами шва совсем другой.

## 6. Модульная экипировка (контракт, без готовой MMORPG-реализации)

**ПРИМЕРЫ:**

| Предмет | Заменяемые регионы базового тела | Действие |
|---|---|---|
| Рубаха другой расцветки того же покроя | `B_TORSO` (+ sleeves если этот покрой имеет их) | другой материал/текстура при идентичных форме и UV |
| Латный нагрудник новой формы | `B_TORSO`; при необходимости `B_UPPER_ARM.L/R` | другая геометрия, но тот же rig contract |
| Тканевые штаны | `B_HIPS`,`B_THIGH.L/R`,`B_SHIN.L/R` | свои сменные части / комплект |
| Металлические поножи | те же, что у штанов | замена mesh по силуэту |
| Перчатки | `B_HAND.L/R`; длинные — также `B_FOREARM.L/R` | замена частей |
| Ботинки | `B_FOOT.L/R`; высокие — также `B_SHIN.L/R` | замена частей |
| Наплечники | `shoulder_mount.L/R` | **навесные** rigid/skinned meshes поверх рукава, не подмена `B_UPPER_ARM` по умолчанию |
| Щит | `shield_mount.L/R` | **отдельное** крепление к предплечью, не заменяет weapon grip |
| Оружие | `weapon_grip.L/R` | **отдельное** крепление к кисти |
| Плащ | `cape_mount` + optional clasps | самостоятельный объект |
| Цельная причёска | `hair_mount` | самостоятельный объект; голова остаётся одной базовой частью |

**Важно:** если вещь визуально занимает область, уже закрытую другой (например высокие сапоги и длинные штаны одновременно претендуют на `B_SHIN`), система не должна отображать обе наружные оболочки. Записать явную `region_coverage` и `priority`. Для предпросмотра: `BOOTS` имеет приоритет на `B_SHIN` перед `LEGS`, `GLOVES` на `B_FOREARM` перед длинным `CHEST`, но у предмета может быть `requires/excludes`; никогда не принимать решение на основе имени меша наугад. В этот этап достаточно **описать и протестировать** конфигурацию в Blender, не писать весь Roblox-пайплайн.

### Материалы и UV
- Для каждой базовой детали сделать рабочую UV-развёртку, без перепутанных островов, сильных растяжений, произвольных поворотов, наложения несвязанных областей.
- Зеркальные области могут делить UV-острова **осознанно** для полной симметрии. Критично не потерять возможность будущих замен текстур; для лица отвести устойчивый остров в `B_HEAD`.
- В рамках базовой версии можно использовать один лёгкий общий atlas до 1024×1024 для базовых body diffuse (либо разделить body+face при объективной причине). **Не нарезать автоматически по одной текстуре на каждый из 15 мешей.** Конкретный atlas layout зафиксировать в документации.
- Все текстуры должны быть физически включены в output bundle и корректно переподключаться при переоткрытии `.blend`.
- Разрешён простейший diffuse; не делать сложных PBR/шейдерных сетей ради красоты.
- Текстурная замена возможна только когда та же mesh topology/UV layout/palette contract; несовместимые UV считаются новой asset-вариацией с явно записанными UV/layout.

## 7. Оптимизация и бюджет

**Предварительные целевые бюджеты, не лимиты движка:**
- Базовый персонаж без волос/экипировки: **примерно 3 000–6 000 triangles** суммарно для 15 body meshes; допускается отклонение если убедительно оправдано качеством локтей/стыков. Стремиться к ~4–5k, не к насильственному урезанию.
- Голова — достаточно граней для гладкого силуэта с простыми ушами/возможной текстурой лица, без высокого скульптинга.
- Точки под суставы тщательно, а в плоских областях геометрия экономная. Проверять реальный triangle count после modifiers/triangulation, не только число quad faces.
- Не создавать десятки ненужных материалов, лишние Subdivision Surface при экспорте, огромные невидимые внутренние цилиндры.
- Жёсткая физическая коллизия — простым отдельным collider/control volume позже; визуальный skinned mesh не должен быть физической collider-моделью.
- Поддержать идею будущей LOD, но не тратить текущий этап на полноценные 3 уровня LOD.
- Прицел на MMORPG-сцену с большим числом персонажей (до 100 игроков на сервер), поэтому минимизировать draw calls, материал-слоты и дополнительные парные объекты **без ущерба контракту заменяемости**.

## 8. Демонстрация модульности (НЕ превращать в изготовление всех комплектов)

Создать **контрольный пакет** — независимый от финального базового тела:

1. `TEST_CHEST_ALT_SHAPE` — намеренно чуть иной силуэт торса (например очень простой нагрудник) на той же арматуре. Выровнен с seam contract. Замена `B_TORSO` не даёт ошибок.
2. `TEST_BASE_TORSO_RECOLOR` — та же геометрия и UV, визуально другой цвет/материал; доказать, что изменение формы не понадобилось.
3. `TEST_SHIELD.L/.R` — зеркальные технические планшеты-щиты с разными тестовыми цветами/сторонами для проверки положений.
4. `TEST_WEAPON.L/.R` — тонкие технические мечи/стержни для проверки независимости оружия от shield sockets.
5. `TEST_PAULDRON.L/.R` — простые тестовые наплечники, независимые от тела.
6. `TEST_CAPE` — простая полоса/прямоугольник с небольшим объёмом, привязанный к верхнему узлу; **не** финальный плащ.
7. `TEST_HAIR_ANCHOR` — временный объём/сфера для проверки `hair_mount`, без прически.

Всё тестовое размещать в коллекции `TEST_ONLY__NO_EXPORT`, скрытой для игрового экспорта, и не оставлять видимым при стандартном открытии основного `.blend`.

### Blender swap preview

Разработать аккуратный проверяемый **тестовый переключатель на Python**: `show_base()`, `show_chest_alt()`, `show_torso_recolor()`, `show_socket_proxies()`. Переключатель только управляет показом альтернативных мешей, а не создаёт новые скелеты. Скрипты и конфигурации должны быть понятными, идемпотентными, без hard-coded Blender scene indexes.

## 9. Test suite и обязательные pose checks

Создать pose/action snapshots (`QA`), возвращать все к rest после теста. Как минимум:

| Тест | Pose | Успех |
|---|---|---|
| `REST_A` | исходная A-pose | полностью симметричная модель, ровные швы |
| `T_POSE` | руки горизонтально | нет переломов на плечах/зазоров между торсом и руками |
| `ARMS_RAISED` | руки вверх ~120° | не разрываются плечевые швы; наплечники двигаются разумно |
| `ELBOW_FLEX` | локти ~90–135° | нет отверстий, сильного коллапса или торчащих caps |
| `WRIST_ROT` | пронация/супинация, сгиб кисти | кисти и предплечья не разрываются, shield tracks forearm |
| `SHIELD_GUARD_L` | левая рука перед грудью в защите | левый щит над предплечьем, оружейная кость справа автономна |
| `SHIELD_GUARD_R` | зеркальный сценарий | зеркально симметричная работа щита на правой руке |
| `DUAL_WEAPON` | по техническому оружию в каждой руке | щитовые сокеты ни на что не влияют |
| `KNEE_FLEX` | оба колена ~100–130° | закрытые швы бедро/голень |
| `SQUAT` | глубокое приседание | таз/бедра не пересекаются катастрофически |
| `STEP_FORWARD` | одна нога вперёд/назад | стыки таз–бедро, бедро–голень стабильны |
| `TORSO_TWIST` | верх 30–45° к тазу | торс/таз без трещин, cape mount следует верхней спине |
| `HEAD_TURN` | голова 60° в обе стороны | шея без отверстий, hair_mount следует голове |
| `MESH_SWAP_POSED` | локти и корпус согнуты, включить тестовый нагрудник | не возникает новый риг, шов остаётся согласованным |
| `TEXTURE_ONLY` | та же форма, заменить текстуру | геометрия и веса не меняются |

**Значение 120°/130° — целевая проверочная поза, не обещание идеально натуральной деформации при любой экстремальной анимации.** Для тестов должны быть изображения viewport solid/wireframe/pose с фронта, сбоку, сзади; фотореалистичные рендеры не требуются.

### Числовая QA (запустить автоматическим Blender Python)

Сделать `scripts/validate_character.py` с exit code nonzero при критическом нарушении и JSON report. Проверить:

- Наличие **всех** обязательных bones, meshes, modifers, materials, UV maps и attachment mounts; их **ровно одна** авторитетная копия в продакшн-сцене.
- Правильные `parent` edges и `use_deform` по контракту; никаких имён `.001` в production, невидимых proxy в экспортной коллекции.
- Симметрия расположения костей (`head/tail`, а также необходимые кватернионы/оси ориентаций для mirrored sockets) с конкретной погрешностью `<=1e-5` в source units или обоснованно записанной.
- Симметрия mirrored vertex positions (например `<=1e-5` units после world→armature space), vertex counts и **отражённых skin weights** (отклонение `<=1e-4`); разрешить специальную обработку поверхности X≈0.
- Surface normals наружу, отсутствие открытых неразрешённых boundary loops, обнаружение degenerate faces, пересчёт alpha z-fighting рисков.
- Отсутствие отрицательных scale, unapplied transforms, рассинхронизации bind matrices между сменными mesh assets.
- Каждый vertex весит суммарно 1±`1e-4`, число ненулевых weights ≤4, не весит на root/attachment; group bone names существуют в rig.
- Точное количество triangles per mesh / total, текстур / материалов / bone count.
- Симметрия UV/материальных назначений пары `.L/.R` или явно разрешённые UV overlapping layouts для симметричного вида.
- Все текстуры существуют в файловой системе либо `pack` в `.blend`.
- Производственные render regions не пересекают границы в rest/poses более допустимого внутри скрытого покрытия; отсутствуют открытые щели. Для швов автоматический geometric gap metric вычислить по seam reference markers; скриншотами проверить очевидные cases.
- Проверить, что переключение торса на TEST_CHEST_ALT_SHAPE **не изменяет bone names, rest pose и base bind matrices**.
- Проверить, что shield_mount не родитель weapon_grip, и они не совпадают в мировом пространстве; shield_mount зеркальны, функциональны в разных позах.

Не допускать **ложноположительной** QA: если проверка недоступна/невозможна без движка, отдельный статус `NOT_TESTED` и конкретная инструкция ручной проверки. Не записывать `PASS`, просто потому что не упало исключение.

## 10. Производственный пайплайн и Blender MCP

Исполнитель управляет Blender **через доступный ему Blender MCP**, при наличии полного доступа `bpy` допускается выполнение **коротких, читаемых локальных Python-скриптов**, а не гигантской «магической» вставки из тысяч строк в один MCP вызов.

### Порядок работы
1. Найти подключённый Blender MCP, проверить tool list, версии Blender/MCP, активную сцену, возможность читать/писать output files. **Не переустанавливать ничего без необходимости**, не запускать сторонние AI-генераторы изображений/3D.
2. Понять ссылки и текущую сцену; создать новую сцену/файл, не удаляя пользовательские объекты и не перезаписывая чужие проекты.
3. Записать `rig_contract.json`, определить rest pose/координаты/mesh regions; зафиксировать структуру коллекций.
4. Смоделировать clean half-body, применить mirror по X с clipping/merge, восстановить нормали, получить по-настоящему симметричные объекты.
5. Смоделировать голову цельной лысой; подготовить face UV zone. Не создавать волосы.
6. Сделать armature: сначала центральную цепь, затем левую половину, симметрировать кости с именованием `.L/.R`, добавить mounts, проверить их локальные frames.
7. Привязать 15 мешей к одному armature, довести веса, создать seam profiles.
8. Настроить материалы/UV с разумным atlas; сохранить рабочий `.blend` и checkpoint.
9. Сделать ограниченные тестовые assets и swap preview, собрать test poses.
10. Выполнить численную QA и визуальное сравнение **с исходным референсом** в solid/material preview; именно ПОСЛЕ исправлений запустить повторную QA.
11. Протестировать экспорт FBX (и GLB при корректном сохранении rig/skins); **повторно импортировать** в отдельную Blender-сцену и сравнить bone hierarchy, transforms, веса, mesh regions и motion. Если отдельный импорт в Roblox недоступен, честно указать, что Roblox-тест остаётся за владельцем.
12. Сохранить файлы и итоговый отчёт; не ограничиваться выводом в чат «я создал».

**Blender MCP безопасность:** выполнение MCP-кода эквивалентно исполнению Python в Blender с файловым доступом. Не предоставлять доступ к приватным каталогам, не запускать code snippets из непроверенных сторонних референсов, делать копии исходной сцены и ограничивать запись внутри каталога проекта.

### Организация `.blend`

```
EYESLAND_CHARACTER_MASTER.blend
  ARMATURE
    ARM_EYESLAND
  BODY_BASE
    B_HEAD
    B_TORSO
    B_HIPS
    B_UPPER_ARM.L / .R
    B_FOREARM.L / .R
    B_HAND.L / .R
    B_THIGH.L / .R
    B_SHIN.L / .R
    B_FOOT.L / .R
  QA_POSES       # actions/pose markers, not extra armatures
  TEST_ONLY__NO_EXPORT  # alt torso and attach proxies; hidden by default
  HELPERS__NO_EXPORT    # optional seams, markers; hidden
```

Blender may internally maintain actions and materials outside Outliner collections. Save `.blend` with neutral rest pose shown, only `BODY_BASE` + `ARMATURE` on screen, optional rig overlay.

## 12. Definition of Done — критерии приёмки

- [ ] При открытии `.blend` виден узнаваемый персонаж из главного референса, но **лысый и строго симметричный**.
- [ ] База нейтральна к полу, тело стройное и пропорциональное; без R15/Roblox-«квадратности».
- [ ] Ровно 15 независимо включаемых/заменяемых base meshes, как в §3.
- [ ] Один `ARM_EYESLAND`, один стабильный rest skeleton contract, корректный weight skinning.
- [ ] Все имена/связи обязательных bones и mounts из §4 присутствуют.
- [ ] Weapon mounts в обеих кистях, **независимые shield mounts на обеих предплечьях**.
- [ ] Отдельные mount bones для наплечников L/R, плаща + симметричных clasp, будущих волос.
- [ ] Левая/правая половины идеально зеркальны **в геометрии, скелете, skin weights и базовом внешнем виде**; различия только в будущих прическах, которых сейчас нет.
- [ ] Корректный UV с подготовленной областью лица; минимальные базовые материалы и texture-only variant.
- [ ] Нет видимых щелей/сильных деформаций на тестовом наборе анимационных поз.
- [ ] Замена торса на другую форму не меняет кости и не ломает анимации.
- [ ] Тест щит+оружие выполняется раздельно на левой и правой стороне.
- [ ] Исходный `.blend`, FBX, отчёты QA, скрипты и референсы находятся в согласованном output каталоге.
- [ ] Нет незаявленных unsupported assumptions, невыполненных тестов, или обещаний будущего выполнения вместо результата.

## 13. Не делать сейчас (строгая граница)

Не разрабатывать прически, facial blendshapes, половые варианты, комплекты брони, полноценный плащ с физикой, высокодетальные руки/пальцы, оружие/щиты высокого качества, боевые анимации, игровую систему инвентаря на Roblox, сетевую синхронизацию, UI/анимационные state machines, интеграцию на live-проекте, причесочные системы и маркетплейс-аватар. Временные QA муляжи — исключительно технические средства проверки.

## 14. Источники: проверенные правила vs наши проектные решения

- Blender Manual — Mirror modifier, Symmetrize, Weight Paint, Armature deform: `https://docs.blender.org/manual/`.
- Blender Foundation Blender MCP Server: `https://www.blender.org/lab/mcp-server/` — официальный альтернативный сервер, с предупреждением об исполнении произвольного Python. Совместимость/version проверить по фактически подключённому MCP; не переустанавливать готовую работающую среду.
- Community Blender MCP: `https://github.com/ahujasid/mcp-for-blender` — другой вариант, есть tool для исполнения кода и предпросмотра; не считать автоматически установленным.
- Roblox Creator Hub — кастомные rigs и import: `https://create.roblox.com/docs/studio/importer`, `https://create.roblox.com/docs/art/modeling/rigging`, `https://create.roblox.com/docs/art/modeling/specifications`. Использовать **Custom**, не привязывать костную схему к R15; ограничение ≤4 influences учитывается для реальной переносимости.
- Lineage II L2J-like Inventory slots: `https://github.com/VytautasBoznis/l2.skilas.lt/blob/master/aCis_gameserver/java/net/sf/l2j/gameserver/model/itemcontainer/Inventory.java` и `https://github.com/rukhavi/l2j-mobius/blob/master/java/com/l2jserver/gameserver/model/itemcontainer/Inventory.java`. Источники относятся к логике equipment paperdoll, **не доказывают** клиентскую skeletal socket-реализацию.

> **Все конкретные имена `shield_mount`, `weapon_grip`, выбор A-pose, parent socket на forearm, лимит полигонов 3–6k и численные tolerances — спецификация Eyesland, а НЕ обнаруженный внутренний стандарт оригинальной Lineage II.**
