# M107 · Real Estate · первая версия authoring pipeline

> **Исторический документ.** Фиксирует состояние на момент указанного этапа; отдельные механизмы могли быть заменены. Действующие контракты: [актуальное ТЗ](../../spec/CURRENT_PROJECT_SPEC_RU.md), [архитектура](../../architecture/CURRENT_ARCHITECTURE_RU.md).


База: `game1_diag_2026-10-17_05-56-47.zip`. Изолировано от NPC/Monster runtime.

## Границы модулей

- `static/real-estate.js/css`, `index.html`: авторинг UI, инвентарь мешей, отдельный выбор текстуры каждого меша из списка либо через Explorer.
- `api/real_estate.py`: только маршрутизация запросов. Native picker в `services/native_pickers.py`.
- `real_estate/contracts.py`: детерминированный нейминг, метаданные покупки/продажи, контракт двух мешей/двух ригов.
- `real_estate/fbx.py`: вызовы Blender, проверка результатов.
- `asset-manager/analyze_real_estate_fbx.py`: инспекция **двух** мешей и отдельных armature с rest transform всех костей; source FBX с пустыми весами допустим.
- `asset-manager/prepare_real_estate_publication_fbx.py`: временный FBX с гарантированной ненулевой привязкой костей, без модификации исходного FBX. Использует `bone_weight_survival.plan_publication_weights` из Character/NPC-пайплайна.
- `real_estate/store.py`: изолированный SQLite реестр, публикация Roblox Open Cloud, манифест. `real_estate/textures.py`: поддерживаемые форматы, каталог и проверка выбранных путей.

## Контракт FBX

Входной файл `house_level1_01.fbx`: объект-MESH `house`, ARMATURE `house_armature` с костями `item_XX_bone`, `chimney_bone` и другими; второй объект-MESH `door`, ARMATURE `door_armature`, обязательная кость `door_bone`. Имена регистрозависимы. Допускается отсутствие vertex groups/skin weights.

При выборе FBX запускается Blender-инспекция, автоматическое заполнение `houseType`, `level`, `variant`. Все три поля редактируемы **до регистрации**, при этом формируют уникальный slug `type_levelN_VV`. Изменение slug уже опубликованного дома — отдельная будущая миграция: первая версия его не выполняет. Для нового slug создайте новую запись.

Отдельно выбирается `.webp`, `.png`, `.jpg` или `.jpeg` для каждого меша. Выпадающий список показывает подходящие файлы рядом с FBX, а **Browse…** открывает Windows Explorer для выбора файла также из другой папки. Регистрация копирует FBX и текстуры под `assets/source/real-estate/<slug>/`, публикуемые ID и карта текстур записываются в `assets/manifests/real-estate.json`. Параметры покупки, продажи и минимального уровня — целые положительные числа с дефолтом 1. Реального списания валюты нет.

## Публикация

Для каждой арматуры применяется существующий 4-influence survival planner; после экспорта временного FBX снова анализируются обе арматуры и сравниваются именование, структура parent и матрицы rest pose. До этой проверки Open Cloud не вызывается. Изображения публикуются отдельными Asset IDs для `house` и `door`; материал исходных мешей получает выбранную текстуру при экспортировании FBX (FBX embed). Если Open Cloud или Roblox Importer не сохранит эмбед текстуры, manifest хранит IDs для будущего Studio texture binder.

**Ограничение:** Blender-подготовка поддерживает сохранение костей за счёт временных ненулевых весов (как у NPC). Для взаимодействий, двигающих сами кости, такая вспомогательная привязка может слегка деформировать часть меша. Автоматической реализации interaction anchors/door animation в рантайме в M107 нет. Никаких гарантий Roblox импорта без реальной Studio/Open Cloud проверки не даётся.

## Совместимость и восстановление

Данные хранятся в **отдельной** `.control-center/game1_real_estate.db`; другие базы и игровые манифесты не изменяются. SQLite миграция первого запуска идемпотентна. Для резервной копии скопируйте DB, манифест `assets/manifests/real-estate.json` и каталог `assets/source/real-estate/`. Откат кода не удаляет данные и Roblox ассеты; для полного удаления новой подсистемы эти три пути можно отдельно удалить после создания резервной копии.

## M107 · форматы текстур, библиотека и Studio Sync (дополнение)

- В выборе остаются WebP/JPG/JPEG/PNG. При публикации Host Agent через Pillow в отдельной временной папке преобразует WebP в PNG **до** сборки FBX и загрузки Image Asset. Канонический WebP не изменяется. Манифест хранит `publicationFormat=png` и исходный хэш; ранее опубликованный WebP без этого поля повторно публикуется как PNG.
- Список зарегистрированных домов справа показывает экономические параметры, FBX/текстуры, статус и действия Edit, Replace FBX, House texture, Door texture, Publish, Sync Studio. Заменив один источник, нажмите **Register / Save**, затем Publish и Sync. Отдельные оригиналы остаются как были.
- Published Model **не** появляется в Studio автоматически из Open Cloud. Для создания шаблона откройте Roblox Studio **в режиме Edit**, включите HTTP Requests, переустановите Game1Bridge после патча и выполните **Sync Studio**. Сервис переиспользует команду `model-load`. После проверки двух мешей, всех ожидаемых костей и привязки двух Image Asset IDs шаблон сохраняется в `ServerStorage/real_estate/<slug>/model/<slug>`. Для сохранения между запусками Studio сохраните Place. Sync отказывает для неподготовленных ассетов и не перезаписывает неуправляемые Studio-модели.
- Roblox Studio Importer может расположить импортированные кости под разными промежуточными группами: модуль проверяет наличие каждого зарегистрированного Bone и количество повторов, но не подтверждает пространственную идентичность каждой ветки. **Действительное сохранение костей и работа скининга требуют проверки на реальном FBX в Studio**.
- Это только authoring + template sync: заселение домов и логика покупки остаются отдельной будущей системой.

## M107 · Исправление конвертации WebP

- Blender занимается только FBX, костями и арматурами. WebP декодируется через Pillow в `real_estate/publication_textures.py`; в Roblox отправляется временный PNG. Оригинальный WebP не изменяется.
- Для Python, которым запускается Host Agent, один раз установите `python -m pip install -r system/control-center/requirements-host.txt`. Устанавливать Pillow в контейнер веб-интерфейса или Blender не нужно.
- Некорректный WebP вызывает явную ошибку до загрузки ассетов. Конвертация не меняет статусы уже опубликованных моделей и текстур.

## M107 · Независимая публикация FBX и текстур (17 октября)

- Реестр хранит три независимых состояния актуальности: `model_sha256`, хэш `house` и хэш `door` (с их собственными опубликованными хэшами). Изменение текстуры не помечает FBX как изменённый.
- После `Replace FBX`, `House texture` или `Door texture` выбор из Explorer **сразу сохраняется** в реестре. Сначала новый источник, затем отдельная команда публикации.
- `Publish FBX`, `Publish house image`, `Publish door image` создают **новый** Roblox Asset ID только для выбранного изменённого ресурса. Публикация существующего ID in-place не используется. `Publish changed` создаёт новые ID только для изменённых ресурсов.
- При выборе нового файла прежние опубликованные ID сохраняются до успешного ответа Open Cloud. История публикаций сохраняет предыдущие ID, а ошибки оставляют прежнюю запись без подмены.
- `Sync Studio` доступен только после успешной публикации всех трёх актуальных ресурсов. Он загружает новую Model ID и назначает две актуальные Image ID.
- Миграция SQLite `user_version=2` преобразует устаревший составной `model_published_hash` в модельный `model_sha256` один раз. В старых записях невозможно однозначно установить, не менялся ли FBX после прошлой публикации: миграция принимает зарегистрированный на этот момент FBX за опубликованный; при сомнении его можно явно заменить и опубликовать снова. После миграции хэши трёх ресурсов всегда независимы.

## M108 — Независимые риги и повторное использование текстур

- Исходный зарегистрированный FBX **не меняется**. Временный Blender-экспорт
  создаёт **два отдельных FBX**: `house.fbx` с `house_armature` и `door.fbx`
  с `door_armature`. Для каждого файла отдельно проверяются состав костей,
  родители, rest-transform и наличие вспомогательных весов для всех костей.
- Публикация FBX создаёт **два новых Roblox Model Asset IDs**; обновление
  существующего ID не выполняется. В случае сетевой ошибки после публикации
  первого рига повторная попытка публикует только недостающий второй риг.
- Исторические записи с единственным общим Model Asset продолжают хранить
  этот ID, но до новой публикации двух ригов отображаются как `UPDATE_AVAILABLE`.
  Текстуры при этом повторно публиковать не нужно.
- Studio Sync загружает две модели, проверяет распределение костей **внутри
  каждого рига**, собирает `HouseRig` и `DoorRig` и только после проверки
  заменяет управляемый шаблон в `ServerStorage.real_estate/<slug>/model/<slug>`.
- В `02 · mesh textures` у каждого меша свой вертикальный редактор. `Reuse`
  выбирает опубликованную текстуру из Location Assets либо текстуру,
  принадлежащую зарегистрированному дому. Переиспользуется **Image Asset ID**,
  отдельный Image Asset не создаётся. Изменения опубликованного ID владельца
  становятся видны без пересохранения Real Estate.
- Если владелец общей текстуры ещё не опубликовал изменённый файл, общий
  Image Asset считается недоступным и публикация/синхронизация дома блокируется.
- Вся существующая работа с файлами WebP/PNG/JPG/JPEG, экономикой, заменой FBX
  и независимой публикацией изображений остаётся на своих местах.

**Ограничение тестирования:** операции Blender и фактический импорт
`AssetService:LoadAssetAsync` требуют Windows/Roblox Studio, поэтому статические
и Python-тесты не доказывают финальный вид и положение двух ригов в Studio.


## M108 Hotfix — необязательные кости и компактный Texture Editor

- Меши `house` и `door` обязательны как две части Real Estate, но кости и
  арматуры могут отсутствовать полностью. При наличии костей их имена,
  родительские связи и rest-transform продолжают проверяться до публикации.
  Фантомные кости для пустого рига не добавляются.
- Желательные кости: `chimney_bone` для house и `door_bone` (также принимается
  авторское имя `doot_bone`) для door. Их отсутствие — **предупреждение**, не
  ошибка. `item_XX_bone` и любые другие имена опциональны.
- При выборе FBX предупреждения перечисляются перед подтверждением.
  Отмена выбора не изменяет зарегистрированные данные. При регистрации
  сервер повторно проверяет согласие с предупреждениями для выбранного FBX.
- Реально найденные кости отображаются отдельно по каждому мешу под
  раскрывающимся блоком, сохраняются в манифесте.
- Арматуры с костями, не принадлежащие ни одному мешу, не отбрасываются молча:
  появляется читаемая ошибка с рекомендацией связать их с нужным мешем.
- `02 · mesh textures` теперь компактный вертикальный список, с выровненными
  колонками и сохранённым режимом Reuse / Browse.
- Blender stderr/traceback не показывается пользователю целиком; API
  сообщает причину ошибки FBX обычным текстом. Проверка в настоящем Blender
  и Roblox Studio остаётся отдельным этапом.
