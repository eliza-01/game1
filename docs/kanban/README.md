# Eyesland Development Kanban — порядок работы

Рабочие документы: `cards/KBN-XXXX.json` + `specs/KBN-XXXX.md`. Постоянный ID карточки **не равен номеру будущего Git-патча**. Номера уже применённых патчей и их подробности сохраняются в `docs/workflows` как история; план не назначает номеров заранее.

## Актуальный фокус

1. **Location Assets**: самостоятельная регистрация и публикация LOD1 (`KBN-0004`, `KBN-0016`). Первый LOD1 `stone_fence_02_lod1` опубликован (Model ID `91896785734146`); требуется Studio/телефон проверка геометрии и переключений.
2. `KBN-0014`: сохранять работающий Collision Blueprint, исправлять только подтверждённые регрессии; не возвращать `col_mesh`.
3. `LOD Manager` (`KBN-0017`): неразрушающий Scan / Snapshot / Readiness над существующим Place Registry. Runtime Build и backup ещё не реализованы, исходный Place не очищать.
4. Distance → LOD, этап 1: pure state policy + Studio-only диагностический probe для одного Location Asset. Это ещё не визуальная выгрузка; затем проверка FULL/LOD1 и пилот клиентского Streaming, серверные коллизии независимы.
5. Android baseline (`KBN-0003`) можно снимать параллельно.

**Пауза:** Real Estate (`KBN-0013`) и тест дома (`KBN-0005`) отмечены ON_HOLD. Их исходная документация остаётся для последующей работы. Не переиспользовать эти карточки под другое назначение.

## Сохранность документов

Старые версии переработанных спецификаций сохранены в `docs/history/kanban_previous_contracts/`. Актуальны только `docs/kanban/specs` и карточки. Архив не использовать как инструкцию к исполнению.

## Правила статусов

Реализовано в коде ≠ проверено в Roblox Studio/на телефоне. В карточках сохраняются `NOT_RUN` без выдуманных PASS. Если локальная база и Git отличаются, приоритет у фактического состояния проекта и подтверждённых оператором проверок. При изменении спецификации обновлять `specSha256`, ревизию карточки и историю принятого решения.
