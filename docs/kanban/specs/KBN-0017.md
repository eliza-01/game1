# KBN-0017 — LOD Manager: инвентаризация и подготовка Runtime Place

**Домен:** World Streaming / Location Assets. **Статус:** в работе; инвентаризация + офлайн Runtime draft для строго проверенной XML-копии. Публикация не реализована.

## Роли и источник истины

- Asset Manager → **Location Assets** владеет регистрацией и публикацией FULL и LOD1. LOD Manager не дублирует этот редактор.
- Studio → **Place Registry Scan** владеет распознаванием размещённых Location Assets по доказанной истории опубликованных Mesh ID и сохранением полных ревизий. LOD Manager повторно использует `LocationPlaceRegistry.operate('scan')`, `PlaceRevisionStore` и существующий Game1Bridge; не сканирует Workspace второй раз и не создаёт собственную базу размещений.
- Авторский Workspace остаётся редактируемым, а Runtime Place должен формироваться отдельной безопасной сборкой **до публикации**. Удаление визуалов при старте сервера не является допустимым Runtime Build.
- Collision Blueprint, Placement ID, Atlas и опубликованные Roblox IDs не меняются при сканировании.

## Первый этап — реализованный контракт

- `GET /api/lod-manager` — только чтение сохранённого последнего снимка и текущего каталога; включает `schemaVersion=1`, `snapshot`, `summary`, `items`, `revisions`, `build`.
- `POST /api/lod-manager/scan` — принимает только `{}` и запускает существующий Place Registry Scan через Studio Edit Mode. Возвращает `scan` и обновлённый `overview`; снимок сохраняется в существующей SQLite истории.
- Каждый зарегистрированный Location Asset показывается, даже если на Place 0 экземпляров. Для распознанных размещений — количество, отсутствие/повтор Placement ID, неоднозначность, отсутствие Model, неполный снимок и расхождение Collision Blueprint.
- Красный индикатор — отсутствует **актуально опубликованный** LOD1; жёлтый — LOD1 опубликован, LOD2 отсутствует; зелёный — опубликованы оба. Регистрация LOD2 ещё не существует; зелёные индикаторы появятся после отдельной реализации LOD2.
- Актуальность: `NO_SNAPSHOT`, `CATALOG_CHANGED`, `SCANNED_THIS_SESSION`, `NOT_LIVE_VERIFIED`. Совпадение дайджеста каталога **не** доказывает отсутствие изменений в Studio; Live-проверка требует Scan.
- История снимков отсылает к существующему JSON с `placementId`, `pivotEvidence`, индивидуальными `CFrame`, `Size`, атрибутами и иерархией. SQLite-снимок не заменяет `.rbxl` backup.
- Скан **не** обнаруживает незарегистрированные / нераспознаваемые по опубликованным Mesh ID объекты. Этот пробел обязательно закрыть до разрешения Runtime Build.
- При совпадении опубликованного Mesh ID скан проверяет **явное авторское владение**. `LandscapeAuthoringTool = Game1LandscapePainter` у Model и `PackageLink` — не DecoManager placements. Они записываются в отдельный `protected` список той же ревизии, без автоматического Placement ID, Repair/Sync/Select или права на удаление. В LOD Manager для каждого вида отображаются стандартные размещения отдельно от защищённых владельцев; у LandscapePainter сохраняются данные Branch Stroke и исходный asset slug, у Package — статус `Unmanaged · Package`. Путь/имя подвеса **не считаются гарантированно стабильным ID**. Runtime Builder обязан fail-closed учитывать `protected` и иные неинвентаризованные объекты, пока не получит независимый подтверждённый контракт.

## Второй этап — безопасный локальный Runtime draft (без публикации)

- `POST /api/lod-manager/preflight` принимает `{}` после Scan в текущей сессии, сверяет `place/game1_runtime_source.rbxlx` (полный Roblox XML Place, сохранённый вручную из Studio) с сохранённой ревизией Place Registry и каталогом. Привязка по полному пути + Mesh ID + MeshPart CFrame/Size + collision CFrame/Size; неизвестная/двусмысленная структура блокируется.
- `POST /api/lod-manager/prepare` принимает одноразовый preflight token и строку `PREPARE RUNTIME`. Проверяет SHA256 исходного файла снова, сначала копирует и проверяет backup, потом создаёт отдельный Runtime XML Place и Placement Manifest; исходный XML не редактирует.
- Первая разрешённая область: **только** опубликованные `stone_fence_02` и `stone_pillar_03`, один визуальный MeshPart + один независимый `__Game1Collision_Part` на модель. Защищённые LandscapePainter/Package, остальные ассеты и дома остаются без изменений. Неизвестные одноимённые Location Models, внешние ссылки на удаляемые MeshParts и отсутствие коллизии запрещают сборку.
- Build output создаётся в новом `.control-center/runtime-builds/runtime_*`, не перезаписывает прежние сборки; включает `authoring_backup.rbxlx`, `runtime_place.rbxlx`, `placement_manifest.json`, `build_report.json` и их SHA256. **`publishAllowed=false`** без исключений.
- Roblox Studio не предоставляет проверяемого сохранения всего открытого Place в отдельный локальный `.rbxlx` из стороннего плагина: поэтому экспорт текущего Place вручную обязателен. Snapshot не подтверждает отсутствие *несохранённых* изменений вне двух разрешённых видов; это блокирующее условие для будущего publish gate, но не для локального черновика.
- Это подготовка Runtime-файла для будущего клиента, **не готовый играбельный Place**. Отдельный клиентский загрузчик, сектора, полный охват мира и подтверждение телефона ещё не готовы.

## Следующий этап — пока не реализован

1. Полное подтверждение покрытия Place (неопознанные Location-кандидаты, коллизии, чужие домены).
2. Проверяемый backup актуального авторского Place с учётом несохранённых изменений Studio.
3. Генерация **отдельной** Runtime-копии Place и Placement Registry из проверенной ревизии, полный rollback и обязательный контрольный повторный scan.
4. Удаление только визуальных компонентов управляемых Location Assets в Runtime-копии; серверные коллизии, скрипты и Gameplay должны сохраняться. Ни Source Place, ни авторские размещения нельзя мутировать.
5. Preview Diff, подтверждение оператора, Runtime Validate и разрешение Publish только после успешной проверки.
6. Клиентский World Streaming и мобильный тест регулируются KBN-0007/KBN-0010, не реализуются внутри LOD Manager.

**Защита:** кнопка Prepare Runtime неактивна до появления проверяемого пайплайна. Никаких Delete, Clone Place, Publish и автоматических очищений в первом этапе нет.

## Приёмка

- В Studio Edit Mode Scan для существующих `stone_fence_02` правильно считает экземпляры и строит сохраняемую ревизию; открытие раздела после перезапуска Host Agent читает её из SQLite.
- Snapshot фиксирует проблемы ID и коллизий, а Scan не меняет ни одного Source Instance.
- Изменение опубликованного Asset Catalog делает последний снимок неактуальным; изменения в Workspace требуют Scan, не выдаём ложный «актуален».
- Перед публикацией: отдельно подтвердить backup, неизменность Source Place и отсутствие визуальных FULL Location Assets в Runtime Place. **Не тестировалось, поскольку Runtime Build не реализован.**
