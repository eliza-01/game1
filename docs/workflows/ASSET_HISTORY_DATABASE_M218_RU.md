# M218 — Database → Asset History (read-only)

**Статус: CURRENT.** Система хранения замен уже реализована в M217
(`ASSET_REPLACEMENT_AUDIT_M217_RU.md`). M218 добавляет в Asset Manager
навигацию **Database → Asset History** и построчную историю Roblox Asset ID.
M218 не изменяет правила Studio Sync из M216, никакого Sync на чтение не вызывает.

## Какие события доступны

Единственный источник для интерфейса — `GET /api/asset-replacements`.
Host Agent сначала идемпотентно импортирует SQLite-истории публикаций в MySQL 8.4,
а затем выдаёт страницы по 200 операций (`nextCursor`/`before`).
Событие Studio Sync для Location Asset содержит slug, предыдущий и новый
Atlas Image ID и/или Model **reference** ID, а также конкретные instance changes
в MySQL. События публикации моделей отображаются как `Model`, публикации
изображений — как `Atlas`, а публикации анимаций — как `Animation`.

Каждое изменение ID показывается отдельной строкой:

- `campfire_01 : Atlas 73384502057808 → 78602158656399`
- `campfire_01 : Model — → 119790979739015`
- `house_level2_01 : Model 123 → 456`

Числа здесь иллюстративные, не реальные опубликованные ассеты. Нажатие на
имя модели копирует **именно `assetKey` / slug**, на старый или новый ID —
**именно число**. Копирование происходит только по нажатию, при отказе
Clipboard API интерфейс сообщает об ошибке (с запасным способом через
`document.execCommand('copy')`). Отсутствующий предыдущий ID — `—` без кнопки.

**Не смешивать типы событий:**

- `studio_sync / model_reference` изменяет только ссылку-метаданные. Геометрия
  MeshPart **не заменялась**, даже если значения ID различаются.
- `studio_sync / atlas` означает применение нового TextureID/ColorMap только
  для выбранного slug, а не для всех потребителей общего атласа.
- Публикация общего `texture_atlas` принадлежит **variant ID**, а не конкретному
  Model slug. В UI это строка «Shared atlas · variant N»: она не выдаётся за
  копируемое имя модели. Определить исторических потребителей такого атласа
  только по журналу публикации нельзя.
- Если прежнего ID нет (первая публикация/первый Sync), отображается `—`.
  Если `oldId == newId`, строка сохраняется: она может отражать публикацию
  новых bytes под прежним ID, а не замену ID.
- Старые события до появления журналирования нельзя восстановить без источника.

Фильтры: domain (на сервере), точный slug/asset key (на сервере),
resource Model/Atlas/Animation (на загруженных страницах). При отсутствии
нужного типа на первой странице «load older events» продолжает поиск.
Навигация `asset-audit` из сохранённых пользовательских предпочтений
автоматически переводится на `database` без потери выбранного раздела.

## Безопасность и обслуживание

M218 меняет только `static/index.html`, `static/character-assets.js`,
`static/asset-audit.js`, отдельный `static/database-history.css`, документацию
и тесты. Нет DDL, миграций, изменений SQLite/MySQL, API, Roblox Studio Plugin
или опубликованных Asset ID. Ошибки MySQL явно видны в интерфейсе; отсутствие
связи с MySQL не маскируется пустой историей.

Для работы нужна MySQL из M217:

```powershell
cd E:\RobloxProjects\game1\system\control-center
docker compose up -d asset-audit-db
```

При недоступной базе проверьте `GAME1_ASSET_AUDIT_*`, `requirements-host.txt`
и Docker. Резервную копию журнала делайте `mysqldump --single-transaction`;
не выполняйте `docker compose down -v`.

## Проверки

`node system/verify/asset_history_database_m218.js` проверяет фактическую
проекцию событий, разделение модели/общего атласа, безопасное HTML-экранирование,
пагинацию, фильтрацию, обработку ошибки MySQL, копирование slug и ID.
Python-обёртка `test_asset_history_database_m218.py` запускается общим набором.
Реальный браузер и работа с установленной MySQL должны быть отдельно проверены
на локальной машине; Studio для read-only интерфейса не требуется.
