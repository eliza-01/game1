# M173 — Characters: модульный UI и границы совместимости

**База:** `game1_diag_2026-10-31_00-05-33.zip`, содержит реализацию Codex `Character Components v1`, `Character Assemblies v1`, `Character Publication Queue v1` и предыдущий M172 для цельных моделей.

## Актуальная модель данных и поведения

- **Rig profile** — общий опубликованный скелет (`human`), не отдельный игровой персонаж.
- **Component** — независимо регистрируемые и публикуемые `upper`, `lower`, `gloves`, `boots`, `head`, `eyes`, `eyebrows`, `hair`; `eyes_*_spiral` — `role=effect` и не является обычным вариантом глаз по умолчанию.
- **Set** — каталогизируемый префикс четырёх clothing-компонентов. Регистрация `new_set_upper` создаёт `new_set` даже без оставшихся трёх частей; неполный set не готов как полный starter outfit. Сохранение рецепта может сочетать части разных set, **не дублируя меши**.
- **Gender** задаётся выбранным `head`; доступные `hair` — matching gender плюс `common`. Броня, глаза и брови не ограничиваются полом. Пол не меняет rig.
- **Character Assembly** — рецепт из восьми слотов, зарегистрированного rig и starting stats. Сохранение не публикует FBX, не запускает Studio Sync, не меняет startup. `Set as Startup` требует серверного `assembly_resolved.ready`, включая фактически опубликованные зависимости; после изменений нужен новый Play spawn.
- **Legacy character** — цельный Model Asset и маршруты M172 `Reg + Publish`; не переводится в assembly автоматически. `human_female` остаётся модельным архетипом, `human_male` уже является assembly **и текущим startup** (проверено по `activeArchetypeId` из дампа 31 октября). Нельзя использовать legacy `Reg + Publish` для отдельных компонентов.

## Новый порядок интерфейса

1. **Rig & parts:** `Choose FBX · inspect` только анализирует. Preview явно различает new/registered/published и перечисляет новые сеты и требующие подтверждения published-name replacements. `Register detected rig & parts` создаёт source-only записи. **Ничего не публикует**.
2. **Publish selected:** только явно выбранные актуально неопубликованные ревизии проходят существующую публикационную очередь; rig — первым. Опубликованный ID сохраняется до успешной замены. Каталог показывает число уже актуально опубликованных и ожидающих новых ревизий. Атлас — отдельный Image Asset, общий для consumers.
3. **Character assemblies:** сохраняет recipe и starting stats одной операцией (`expected_revision`). Starter set заполняет 4 clothing slots; их можно изменить поштучно. UI показывает фактическую смешанность комплекта, gender-подсказки, наличие Model IDs и недостающие зависимости. Это **предварительная клиентская оценка**: окончательное решение `READY` и разрешение startup остаются на сервере.
4. **Set as Startup:** доступна только готовым записям, не вызывает повторную публикацию. `New assembly` в левой панели создаёт рецепт, не цельный legacy character. Legacy-редактор скрыт отдельно и доступен явно.

Редактирование recipe и stats имеет dirty-state/Reset; Refresh и успешные публикации не затирают несохранённые правки. При переключении сборки запрашивается подтверждение потери правок. `Save` не активна без изменений в существующем рецепте.

## Ограничения M173 — сознательно не изменены

- Не выполнялась окончательная миграция legacy (`human_female`) и не удалены старые endpoints, таблицы, поля, Model IDs и Animation Registry. Совместимость необходима до самостоятельного проекта миграции с upgrade/rollback.
- Нет объединённой ACID-транзакции SQLite/Roblox Open Cloud/Studio. Publication Queue продолжает существующую idempotency/recovery.
- Client preview readiness **не доказывает** сохранность `Bone`/bind позиций после Roblox import, наличие атласа в Studio или корректность анимаций. Приоритет — серверный resolver и Studio Play на фактически опубликованных assets.
- В M173 не менялись миграции, серверная валидация, runtime CharacterAssemblyBuilder, анимации, mesh source и rig bone data.

## Проверить после патча (Windows)

1. Открыть Characters: слева **New assembly**, сверху workflow в порядке Inspect → Publish → Assemble → Startup, legacy цельный FBX под отдельным раскрывающимся блоком. Нажать на legacy в дереве: раскрывается именно legacy-форма.
2. Без выбора FBX `Register detected rig & parts` недоступна. При `Choose FBX · inspect` предварительный список показывает обнаруженные части/новые сеты и что регистрация ещё не произошла. Тестировать безопасно на копии FBX; не подтверждать замену опубликованных компонентов без намерения.
3. Текущий каталог: один зарегистрированный set `newborn`, опубликованный `human` rig и части. В публикационной таблице актуально опубликованные строки нельзя повторно выбирать, не должно происходить повторных upload.
4. Открыть `human_male`: `newborn` заполняет четыре clothing slot; можно выбрать другой опубликованный `boots`, если такая часть уже зарегистрирована. Появляется `mixed` и зелёная Save. Нажать Reset: возвращается исходный рецепт и Save недоступна. Для локальной проверки можно изменить число starting stats, сбросить; не обязательно сохранять в DB.
5. Сменить head: волосы другого пола перестают быть допустимыми, `common` остаются. Не выбирается служебный `eyes_01_spiral`.
6. Доступный `Set as Startup` на `human_male` — только при `READY`; без явного нажатия startup остаётся текущим `human_male`; повторный Set as Startup для него неактивен. Для реальной проверки переключения — принять намеренное изменение, перезапустить Play и проверить сборку. Неизменённые legacy ID должны сохраниться.
7. Запустить `python system/verify/verify.py` (exit 0), `python -W error::ResourceWarning -m unittest discover -s system/verify -p 'test_*.py' -q`, `node --check` для изменённых JS.
