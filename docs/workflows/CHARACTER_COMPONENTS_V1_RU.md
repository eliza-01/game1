# Characters: регистрация рига и частей, v1

> Актуальный порядок интерфейса: [M173 — Modular Characters](CHARACTERS_MODULAR_UI_M173_RU.md).

Область: новый блок **Characters → Rig & parts**. Регистрация, подготовленные FBX,
публикации компонентов и ссылки на общий Atlas Registry. Анимации, runtime-сборка,
параметры боя, startup и сохранения игроков этим этапом не меняются.

## Имена

Все новые идентификаторы — ASCII lower_case_snake_case, без `.001`.

| Сущность | Имя |
|---|---|
| Основной скелет | `<profile>_armature`, например `human_armature` |
| Верх | `<set>_upper` |
| Низ | `<set>_lower` |
| Перчатки/кисти, пара | `<set>_gloves` |
| Ботинки, пара | `<set>_boots` |
| Голова | `head_01_male`, `head_01_female` |
| Причёска | `hair_01_male`, `hair_01_female`, `hair_01_common` |
| Глаза, пара | `eyes_01` |
| Брови, пара | `eyebrows_01` |
| Спираль глаз, служебный эффект | `eyes_01_spiral` |
| Собственный скелет причёски | `<имя_причёски>_armature` |

Индексы начинаются с 01. Имена сетов могут включать подчёркивания: парсер
определяет слот по последнему суффиксу. Сет `newborn` содержит
`newborn_upper`, `newborn_lower`, `newborn_gloves`, `newborn_boots`.
Пол не относится к телу/сетам. Спираль имеет `role=effect`, не подменяет обычный
выбор формы глаз. Тестовые/дизайнерские объекты не входят в регистрационный FBX.

## Работа

1. **Choose FBX · inspect**: выбирает файл, фиксирует его байты в staging,
   читает armature, имена мешей, веса, UV/геометрию и bind-структуру.
   Показывает список частей и автоматически определённые новые сеты.
   Инспекция не регистрирует риг/части и не обращается к Roblox.
2. Если имя части уже опубликовано, открывается модальное окно. Нужны отдельные
   флажки подтверждения всех включённых опубликованных частей. Даже совпадающий
   контент не означает неявного разрешения перезаписи.
3. Для неизменённых частей: отменить, исключить соответствующие меши из FBX,
   выбрать исправленный файл. Отсутствие меша не удаляет запись из каталога.
4. **Register detected rig & parts**: создаёт/повторно использует профиль рига,
   регистрирует части, автоматически создаёт сеты и извлекает отдельный FBX
   каждой части. Совместимый существующий риг используется повторно.
5. **Publish** — отдельное явное действие над каждой записью. Регистрация сама
   ничего не загружает в Roblox. Повторная публикация текущей ревизии — no-op.
   Подтверждённая замена создаёт новую локальную ревизию; прежний Model ID
   остаётся назначенным до успешной публикации нового. История сохраняется.

Все части FBX должны иметь один Armature modifier и 1–4 положительных
нормализованных веса на вершину. Неизвестные/дублирующиеся имена отклоняются.
Основной FBX содержит полный эталонный `human_armature`; можно исключать меши,
но нельзя незаметно менять кости, родителей и bind-матрицы зарегистрированного
профиля. Другой скелет регистрируется под новым именем профиля.

Собственный риг волос сохраняется вместе с частью; для связи с основным
персонажем записывается `hair_mount`. Реальная сборка и посадка волос в игре
будут отдельной реализацией, регистрация этого не имитирует.

## Данные и атомарность

- Таблицы `character_component_*` добавляются в `.control-center/game1.db`.
  Старые `characters`, их Model IDs и анимационные таблицы не мигрируют.
- Перед первым добавлением таблиц SQLite online-backup записывается в
  `.control-center/backups/before_character_components_<id>.db`.
- Полный входной FBX: `assets/source/character_components/imports/<import_id>/source.fbx`.
- Извлечённые FBX: `assets/source/character_components/<import_id>/`.
  Это канонические входы публикации: проект использует source-only storage,
  а `assets/prepared` очищается существующей startup-миграцией. Поле
  `prepared_path` обозначает извлечённый файл, но указывает на `assets/source`.
- Генерируемый каталог: `assets/manifests/character-components.json`.
  Источник истины — SQLite; JSON не редактировать вручную.
- Extraction предшествует одной транзакции регистрации. Ошибка extraction
  не изменяет каталог. Повторный commit того же inspection token идемпотентен.
- Проверяются ревизии и опубликованные ID между inspect/commit. Конкурентная
  регистрация или публикация требует новой инспекции и нового подтверждения.
- Предыдущие записи и пути сохраняются в `character_component_history`.
  Для отката отдельной части восстанавливаются её прежние metadata/paths/ID
  из history в транзакции. Полный DB backup нужен для аварийного отката всего
  состояния; не восстанавливать его поверх более новых несвязанных правок.
- После получения Open Cloud operation path он сохраняется. Повтор после
  таймаута опрашивает эту операцию и не создаёт второй upload. Окно аварии
  между ответом create и записью operation остаётся ограничением внешней API:
  перед повтором после такого crash требуется сверка истории Roblox.

Риг извлекается с отдельным `rig_carrier`: служебные треугольники с весами 1.0
сохраняют полный набор костей без добавления лицевых весов на одежду.
Видимые части сохраняют свои веса и получают только используемые кости и их
предков. Для будущего runtime carrier должен быть невидимым, неколлизионным и
постоянным. Текущий этап не добавляет его в игровой spawn и не утверждает
проверку Open Cloud/Studio skinning.

## Атласы

Используется существующий `AtlasRegistry`, тот же, что в Location Assets:
`<atlas_key>_<width>x<height>_atlas.png/jpg`. Consumer type — `character_part`.
Общая семья/вариант имеет один Image Asset ID, части хранят только binding.
Регистрировать/публиковать атлас можно в новом блоке или в Location Assets.
Выбор опубликованного варианта проверяет optimistic binding revision.
Без атласа допустим исходный одноцветный материал.

Изменение binding не перепубликовывает меш. Studio Sync/применение appearance
к собранному персонажу не входит в этот этап; ссылки не следует принимать за
уже применённую текстуру на игровом экземпляре. При замене общего атласа каталог
берёт актуальный опубликованный Image ID из общей записи.

## HTTP v1

- `GET /api/characters/components`: риги, части, сеты, atlas catalog.
- `POST .../inspect {sourcePath}`: token и preview, конфликты опубликованных имён.
- `POST .../register {token,replacements:[part_id]}`: commit всей инспекции.
- `POST .../publish {kind:"rig"|"part",id}`: отдельная публикация/возобновление.
- `POST .../atlas {id,variantId,expectedRevision}`: привязка общего атласа.

Host Agent authentication сохраняется. Конфликт состояния возвращает HTTP 409
с `code=inspection_conflict`; ошибка входа/подготовки — HTTP 400. Старые endpoint
Characters и существующий анимационный раздел сохраняются.

## Blender human.blend

Файл создан рядом с `human_male_backup.blend`, который остался без изменений.
Production-коллекция `human`: `rig`, `sets/newborn`, `heads`, `face_parts`,
`hairstyles`. `sources` и `tests` отделены и не включаются в экспорт.
Вторая причёска объединена из прядей в `hair_02_common`; редактируемые пряди
сохранены в `sources/hair_02_designer_source`. Не экспортировать весь файл
без фильтра: выбирать production `human`. Оба альтернативных hair-меша
включаются в регистрационный FBX, хотя в viewport видна только одна причёска.

В новой копии нормализованы относительные веса верха/перчаток. У hair_01
исправлены 3 UV-полигона и разъединены неоднозначные неманифолдные стыки без
перемещения поверхности. Совпадающие вершины разных прядей/оболочек и общие
UV волос оставлены намеренно; глобальный Merge by Distance не выполняется.
Имена костей, rest pose, масштабы и анимационные данные не переделывались.
