# M255 · Location Assets без служебного RootPart в Studio

## Причина

Публикация цельного FBX со скелетом может создать в Roblox невидимый
`Part` с именем `RootPart`. В старых декорациях под ним находятся корневые
`Bone`, а импортированные `Motor6D` связывают его с визуальным MeshPart и COL.
Это НЕ компонент системы размещения DecoManager: он приходит из опубликованного
Model Asset. Прямое удаление Part теряет связи костей, коллизию и pivot.

Real Estate собирает проверенные отдельные mesh rigs, а не требует такого
дополнительного физического корня. Общая технология замены существующего
управляемого rig (`StudioManagedRigSwap`) не меняется.

## Где применяется

- `StudioLocationImportRoot` — независимая проверка, нормализация и rollback.
- `DecoAssetLoader` — нормализация свежей опубликованной Location Model **до**
  её размещения или использования в Studio Sync. Публикация в Open Cloud и
  исходный FBX не меняются.
- `StudioPlaceRegistryInventory` — предупреждение для старого размещения,
  `needsStructure`, блокировка Sync до Repair.
- `StudioPlaceRegistryRepair` — **явная**, журналируемая/Undo-операция,
  которая сначала восстанавливает недостающий COL, затем убирает RootPart.

Real Estate, Character, NPC, Monster и прочие модели не участвуют.

## Допустимые условия

1. В Model присутствует ровно один **визуальный** MeshPart; дополнительные
   MeshPart могут быть COL, но не вторым визуальным rig.
2. `RootPart` — невидимый `Part`, а не авторская/игровая геометрия.
3. Все прямые дети `RootPart` являются `Bone`. Неизвестные Weld/Constraint,
   внешние соединения и неописанные `Motor6D` запрещены.
4. Импортные `Motor6D` соединяют Part с внутренними MeshPart; их замена
   разрешена только после проверки.
5. Удаление RootPart не должно уничтожать единственную физическую коллизию.
   При наличии нового обязательного COL его восстанавливают сначала.

Неподдерживаемые случаи отклоняются **до** размещения/изменения Place.
Для многовизуального/нестандартного rig нужен отдельный, проверенный план
публикации (как у Real Estate), а не принудительный перенос костей.

## Какие свойства сохраняются

- Мировое положение и текущая поза (rest/pose) корневых Bone.
- `CFrame` и `Size` каждого MeshPart.
- Pivot размещённой Model.
- Дочерняя иерархия Bone; имена костей и MeshPart, Mesh/Texture/Atlas IDs.
- Жёсткая связь визуального меша и COL через `WeldConstraint` после удаления
  импортных `Motor6D`.

При ошибке `Apply` восстанавливает исходные Parent/CFrame, Motor6D,
PrimaryPart/Pivot и удаляет созданные WeldConstraint. Repair ведётся через
`ChangeHistoryService`; после успешной транзакции запись доступна в Undo.

## Обязательная проверка на копии Place

1. Открыть один **новый** Location Asset с одним skinned MeshPart и COL через
   DecoManager. Проверить отсутствие `RootPart`, расположение Bone под
   визуальным MeshPart, `CFrame`, COL и отсутствие смещения.
2. Проверить позы Bone в Animation Editor/Play. Скриптовые проверки **не**
   могут доказать, что skinning Roblox не изменился.
3. Для одного **старого** размещения выполнить Place Registry Scan → Repair,
   повторить Scan, сравнить `CFrame`, `Size`, `Pivot`, связь COL и Undo.
4. Отдельно проверить неравномерно масштабированную модель, старый объект с
   недостающим COL и физически привязанный объект: опасный случай должен быть
   отклонён с сообщением, а не частично изменён.
5. Только после этих проверок допускается групповая миграция.

**Важно:** опубликованный бинарный Model Asset ID остаётся неизменным, даже
если внутри него Roblox по-прежнему содержит импортный RootPart. Изменяется
его безопасно подготовленная копия в Studio, а не исходный файл в облаке.
