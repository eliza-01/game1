# M252 · Location Place Registry · reconciliation consistency

## Дефект и подтверждённые данные

В диагностике 2026-11-07 ассет `campfire_01` (исторический slug
`campfirte_01`) имеет опубликованные версии:

- Model `119790979739015`: visual Mesh `70451663424090` ×1;
- Model `85955870892092`: тот же visual Mesh `70451663424090` ×1 + COL Mesh `119159216521971` ×1.

Размещённый экземпляр содержит старый visual, Bone и эффект Fire, но не COL;
атрибут `Game1DecoPublishedModelAssetId` указывает на прежнюю публикацию.
Прежняя диагностика принимала совпадение *одного* visual MeshId за актуальность
всего rig, считала идентичность версии неоднозначной и блокировала Sync из-за
отсутствующего COL. Repair пропускал восстановление COL при `needsMesh=true`,
даже если изменение было исключительно добавлением коллайдера.

## Распределение ответственности

- `StudioLocationPublishedGeometry`: read-only сопоставление полной мультимножества
  MeshPart с сохранёнными публикациями, выбор достоверного старого Model ID.
  Атрибут старой публикации используется только как подтверждение при нескольких
  идентичных *полных* инвентарях.
- `StudioPlaceRegistryInventory`: положительный allowlist зарегистрированных
  Location Assets, отдельные статусы `needsMesh` (visual) и `needsRig`
  (состав опубликованной модели, в том числе COL). Сканирование не изменяет Place.
- `StudioPlaceRegistryRepair`: восстановление обёртки, имён и ID; отдельное
  аддитивное восстановление COL, когда visual MeshId соответствует текущему.
  Bone/Fire на визуальном меше сохраняются. Восстановление COL допустимо только
  для **однозначной** пары visual+COL и закреплённого visual. Любые непроверенные
  внешние связи COL, неоднозначная старая публикация или недопустимые масштабы
  останавливают операцию; автоматический полный rig swap не подменяется клонированием.
- `StudioPlaceRegistrySync`: отдельное применение устаревшей геометрии,
  Atlas, Alpha и Surface Material. Используется существующий `StudioManagedRigSwap`;
  Real Estate не изменён. Repair не переписывает Material вместо Sync.
- `StudioLocationPlacementHistory`: единая ограниченная запись истории внутри
  размещённой Model для Repair/Sync. SQLite-журнал Place Registry и штатная
  история Roblox Studio остаются ответственными за Undo.

## Безопасность и UX

При добавлении COL исходный визуальный MeshPart не заменяется. Сохраняются его
CFrame, Size, PivotOffset, Bone и Fire. Коллайдер выставляется по матрице
относительного размещения текущего опубликованного visual+COL и сохраняет
индивидуальный неравномерный масштаб. Коллизия старого visual отключается,
чтобы не допустить двойных столкновений, и восстанавливается через Undo.
`col_mesh` остаётся без Texture/SurfaceAppearance.

Импортированный FBX может хранить внутри `col_mesh` технический `Motor6D`,
ссылающийся на импортный `RootPart`. Для аддитивного восстановления
такая связь допустима только когда сам соединитель принадлежит поддереву
COL: в автономном Anchored-клоне он удаляется после вычисления CFrame.
Соединитель, принадлежащий любому другому поддереву rig, по-прежнему
блокирует Repair.

`Repair` теперь возвращает `changed=0` для уже корректной структуры. Когда
невозможно подтвердить старую Model-публикацию, в журнале сохраняется причина.
После Repair интерфейс повторно сканирует Place: оставшиеся Material/Alpha
несоответствия устраняются **отдельным** явным Sync.

## Проверка перед реальным применением

1. Создать резервную копию Place (`.rbxl`).
2. Scan `campfire_01` — ожидаются `COL отсутствует`, `Rig отличается`,
   подтверждённая предыдущая Model-публикация, Repair доступен.
3. Repair только одной модели: visual CFrame/Size/PivotOffset и Bone/Fire
   без изменений, COL присутствует, visual CanCollide=false, COL CanCollide=true.
4. Повторный Scan: расхождение по полной Model-геометрии исчезло; отдельно
   остаются Material/Alpha, если они отличались.
5. Sync только этого размещения и Undo через журнал.
6. Повторить Repair актуальной модели: действий быть не должно; регрессии
   Real Estate Edit/Sync тестировать отдельно.

Автоматическая миграция всей карты, массовое изменение неизвестных моделей,
восстановление динамических/связанных COL и полное восстановление `.rbxl` по
SQLite здесь **не реализованы**. Реальную Studio-проверку необходимо выполнить
локально: static preflight не эмулирует физику Roblox.
