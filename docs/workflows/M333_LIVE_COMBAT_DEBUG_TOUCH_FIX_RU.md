Состояние: изменение относительно фактического дампа `game1_diag_2026-11-13_12-17-45.zip`.

## 1. Причина потери урона

`HitboxMeshGeometryCache` запрашивает `AssetService:CreateEditableMeshAsync` при спавне. В Studio с отключённой настройкой API или в опубликованном Place при недостаточных правах движок отказывает в доступе к геометрии. Ранее `EntityHitboxService.Attach` прекращал создание хитбоксов на первой ошибке, даже если имелся готовый `RootCollider`.

M333 сохраняет **один** механизм авторитетного урона: `EntityHitboxService` / `HitboxSpatialQueries` / `DamageService`. `HitboxDefinitionBuilder.Fallback` строит консервативные OBB по `RootCollider`, без новых физических Part и без нового расчёта урона. Если возможно, добавляется небольшой head OBB вокруг `head` кости; если нет — только body. При доступном EditableMesh алгоритм точных bound-OBB не меняется. Runtime атрибуты: `CombatHitboxMode = root_bounds_fallback`, `CombatHitboxCount > 0`, `CombatHitboxFallback = true`. Геометрия приближённая; возможны попадания в пустые края bounding box. Для точной поверхности необходимо разрешение EditableMesh API в Security и доступ к исходным mesh assets.

Важно: добавление серверного fallback не меняет урон, дальность Bow Hitscan, смерть/фантомность монстров и механизм попадания нескольким целям.

## 2. Опубликованный тестовый Place: кнопки разработчика

`Options → Debug and test controls` управляет показом для PC/Mobile **независимо**, но опубликованный Place должен быть заново синхронизирован и опубликован. M333 снимает безусловный `IsStudio()` только с debug интерфейсов; их RemoteFunctions проверяют серверный атрибут, который устанавливает `PublishedDebugAccessService` после проверки Roblox CreatorId (user owner или доверенного администратора группы с rank >= 200). Для обычных игроков debug-панели скрыты и серверные отладочные запросы отклоняются независимо от UI. В Studio Play штатная работа не меняется. Меню оружия использует этот же доступ и `WeaponSelectionService` дополнительно проверяет его на сервере.

При опубликованном group-owned Place у участника группы с рангом ниже 200 кнопки не появятся, даже если галочка включена. Нельзя давать серверные отладочные операции всем игрокам только по локальной галочке. Если требуется доступ другим тестировщикам, нужен отдельный защищённый перечень ролей.

## 3. Mobile camera

- Палец может начинать вращение только в правых 2/3 экрана, включая прежнюю невидимую область правого стика.
- Левый stick и UI-кнопки не перехватываются камерой.
- При двух одновременных touch inputs выполняется pinch-to-zoom; после отпускания одного пальца не начинается однопальцевый zoom / rotate. Новый жест начинается после отпускания обоих пальцев.
- Скорость вращения = `CharacterConfig.CameraTouchSensitivity × GameOptions.MobileCameraSpeed()`. По умолчанию ×1.5; допустимый диапазон Options 0.25–4. Нет инерции. Mouse PC не меняется.
- `OptionsStore` дополняет существующую camera конфигурацию значением `mobileLookSpeed` при запуске, не сбрасывая authored fields, пресеты, HP или остальные Options.

## 4. Проверка в Roblox Studio и опубликованной игре

1. В Studio проверить `CombatHitboxMode` и `CombatHitboxCount` на Gremlin, NPC и персонаже; при запрете EditableMesh должно быть `root_bounds_fallback`, count > 0. Провести серию ударов/выстрелов PC/Mobile, урон и смерть должны проходить. При включении API режим может быть `precomputed_bone_boxes`.
2. В `Options` сохранить published debug controls для PC и Mobile, перезапустить Rojo-синхронизацию и сделать **Publish to Roblox** в конкретный Eyesland Dev/TestPlace. Убедиться, что на учётной записи владельца появились кнопки; на обычном игроке — нет.
3. На телефоне: тест свайпа справа/слева, одиночного пальца, одновременной ходьбы и обзора, щипка, отпускания одного пальца, повторного жеста; проверить скорость ×1.5 и сохранение через Options.
4. Поскольку мы не запускаем Roblox Studio в этом окружении, успешные Python/статические тесты не подтверждают фактическую работу анимаций, физики и мобильных touch событий на устройстве.
