# M348 · Location Collision: stable pivot anchoring and inventory detection

## Причина

В дампе 2026-11-14 17:24 сохранены три ревизии `stone_fence_02`.
Первая создана из обычного `Part`, а следующие — из `__Game1Collision_...`.
Такое повторное Capture уже созданных частей приводило к изменению сохранённого
`localCFrame`. При этом исходный Model может использовать PrimaryPart/PivotOffset,
а новая опубликованная Model — WorldPivot, без общего начала координат.

## Контракт M348

- Сохранённый Blueprint остаётся в локальных координатах `Model:GetPivot()`
  выбранной размещённой модели и не меняет ни оригинальную геометрию, ни Pivot.
- Формат **schemaVersion 2** дополнительно сохраняет `anchor` — уникальный
  опубликованный визуальный Mesh ID, размер MeshPart и его `CFrame` относительно
  исходного Pivot. Этот ID должен присутствовать ровно один раз в текущей
  публикации и в выбранном экземпляре. Равенство только имени не достаточно.
- При генерации новая Model находит тот же визуальный MeshPart и вычисляет
  виртуальный Pivot исходной модели через сохранённый `anchor.localCFrame`.
  FULL, PivotOffset/PrimaryPart и WorldPivot не требуют компенсации вручную.
- По трём осям эталонного MeshPart проверяется коэффициент одинакового
  (uniform) изменения Size. Он определяет коэффициент для координат/размеров
  всей коллизии, в том числе при ручном изменении размера MeshPart вместо
  Model:ScaleTo(). Неодинаковый масштаб по осям блокируется до мутации:
  нужно повторное Capture с актуальной публикации.
- Повторное Capture `__Game1Collision_...` запрещено. Выделять нужно
  **оригинальные авторские Parts**, а не порождённые системой коллайдеры.
- При Scan отсутствие полного набора управляемых коллайдеров, ревизии, SHA,
  размеров или позиции обнаруживается независимо от наличия самого Part.
  Если нельзя определить Model, результат диагностики отображается, но Sync
  не разрешён до нормализации Placement.
- Старые Blueprint schema 1 сохраняются в истории SQLite, но **не применяются**
  после обновления. Требуется один новый Capture; никаких автоматических
  исправлений координат устаревшей записи не делаем.
- Sync меняет коллизию в отдельной undo-записи. Предыдущие Parts выводятся
  из Workspace через Parent=nil, а не Destroy() после записи истории.
- Вместе с заменой полного rig Collision Sync получает геометрию
  **нового** опубликованного rig, не старого, для поиска эталонного Mesh ID.
- Real Estate, FBX, Plot bindings, published Asset IDs и Blender не меняются.

## Проверка в Studio

1. Обязательно сохранить копию Place перед проверкой.
2. Для `stone_fence_02` подготовить **оригинальный** Part / WedgePart,
   выделить его и один экземпляр `stone_fence_02` одновременно.
3. Asset Manager → Location Assets → Collision Blueprint:
   `Validate → Capture`. В истории появляется schema 2 (ревизия +1).
4. На том же экземпляре проверить Preview. Parts должны совпасть с оригиналом.
5. Place Registry → Scan Place. У существующих экземпляров без Parts
   должен появиться `Collision ✕ требует Sync`; затем Sync All.
6. DecoManager → Place: поставить новый экземпляр под разными углами,
   сравнить коллизию с моделью. Использовать также объект, у которого
   PrimaryPart задан, и другой без него. Нормализовать Pivot вручную нельзя.
7. Удалить один из созданных `__Game1Collision_...`, повторить Scan:
   экземпляр должен снова перейти в `требует Sync`.
8. Запустить Collision Sync и проверить Ctrl+Z/Redo. Только после успешной
   ручной проверки решать о массовом Sync.

## Границы автоматических проверок

Python-тесты проверяют сохранение, формат, идентификацию текущей публикации,
ошибки старого контракта и интерфейсную диагностику. Они не исполняют физический
движок Roblox или Luau. Положение, поворот, масштаб и Undo требуют ручного
подтверждения в Studio до массового применения.
