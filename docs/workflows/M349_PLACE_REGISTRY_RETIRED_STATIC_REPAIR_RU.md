# M349 · Place Registry: распознавание старых статичных размещений после удаления COL

## Контекст

После M342 (отказ от COL) в истории публикаций могут сохраняться невизуальные
Mesh ID старого COL-меша. В рабочем Workspace соответствующая геометрия уже
удалена. `History.MatchesInventory` сравнивал *полный* набор Mesh ID, из-за
чего переставал узнавать существующую внешнюю Model (например,
`stone_fence_01__f60a3f13`). Затем Scan показывал «Нет отдельной Model» и
«Нет Placement ID», но `canRepair=false`, `canSync=false`.

В дампе 2026-11-14 19:17 публикация `stone_fence_01` 127322907067835
содержит в истории Mesh ID 139744616815788 (визуальный) и
101609374432019 (старый невизуальный). В Place Registry у существующих
размещений остался один визуальный MeshPart. Это объясняет потерю распознавания.

## Изменение

Введено строго ограниченное сопоставление `MatchesRetiredStaticInventory`:

- действует лишь для доказанно статичных публикаций (legacyStaticPublication
  либо `rigManifest.rigKind=static`);
- сравнивает весь *оставшийся* набор визуальных Mesh ID с опубликованной
  исторической версией, сохраняя количества, а не один совпадающий ID;
- требует явную границу конкретного размещения: именную Model `slug__XXXXXXXX`
  или корректную метку Game1DecoAssetSlug; чужая метка и вложенные размещения
  блокируют применение;
- применяется лишь когда в исторической версии были невизуальные MeshParts;
- неоднозначность исторической версии запрещает Repair.

Обычная строгая `MatchesInventory` осталась неизменной для всех иных случаев.

## Последовательность

1. `Scan Place`: восстановление распознавания внешней Model без модификации Place.
2. `Repair` на **одном** распознанном экземпляре: только ID/имя/метки,
   без перемещения модели, изменения MeshPart.Size, CFrame, PivotOffset,
   Model:GetPivot, PrimaryPart или Scale. Единая запись Undo.
3. Новый `Scan Place`: подтвердить уникальный Placement ID.
4. `Sync` на **том же** экземпляре: восстановить Collision Blueprint по
   визуальному Mesh anchor после независимого preflight.
5. Повторно проверить визуальное совпадение коллизии, Ctrl+Z и только затем
   разрешать групповую миграцию.

## Чего M349 не делает

- Не преобразует PivotOffset старого меша в PivotOffset новой публикации.
- Не перезаписывает WorldPivot или PrimaryPart ради внешнего сходства.
- Не предполагает, что Model Pivot и MeshPart Pivot обязаны совпадать.
- Не заменяет полный rig и не возвращает устаревшие COL.

Это **первый безопасный этап** восстановления работоспособности Repair/Sync.
Сопоставление старых и новых локальных систем координат требует сырой снимок
Place с WorldPivot, PivotOffset, GetPivot и CFrame. Если PivotOffset менялся
в прошлых Sync, его нормализация должна применяться только после проверки
точной обратимой трансформации на одном объекте.

## Отказобезопасность

Неподтверждённые группировки, скелетные риги, конфликтующие исторические
версии и несоответствие состава визуальных MeshParts остаются заблокированы.
Repair не удаляет объекты. Scan остаётся read-only. Ни один массовый
Repair/Sync не инициируется автоматически.
