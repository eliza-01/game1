# M628 · MNPC Entity-first Lifecycle Foundation — шаг 1

**База:** свежий диагностический дамп `game1_diag_2026-11-28_05-08-35.zip` (M627, KBN-0037 rev17). Включены согласованные документационные уточнения rev18–19, так как их ещё нет в дампе. Рабочая карточка KBN-0037-T08/A07 открыта. [Актуальное ТЗ MNPC](MNPC_LOD_SPEC_RU.md).

## Реализовано

- `actor/MnpcEntityLifecycle`: один API для обоих spawn entrypoint. `Create(name,surface,yaw,kind)` не принимает template и создаёт новый Model с `Game1MnpcKind`/`Game1MnpcRigReady=false`, технический корень и Humanoid. Template metadata копируются отдельно; тип и readiness не импортируются из ассета. `AttachRig` и `Publish` делегируют отдельным владельцам. `MarkRigReady` вызывается после прежних full-pose/hitbox preparation, не означает, что actor damageable (например MonsterSpawning).
- `actor/MnpcNavigationShell`: одна реализация физического тела 2×2×1, hip 1,8, высота над surface 2,8, server ownership при публикации, существующий ActorCollisionPolicy; NPC-only запрет FallingDown/Ragdoll M422 сохранён. Без MeshPart/Bone/Animator/RootCollider/шаблона. Сущность может быть создана без визуала; никакой новый runtime scheduler не введён.
- `actor/MnpcVisualRig`: клонирует исходный template отдельно от entity, подготавливает detached rig, сохраняет исходную иерархию, ground alignment и только затем подключает к уже существующему корню. Не делает PivotTo(entity). Canonical ImportedRig сохраняет структуру; unwrapped Model становится ImportedRig. Не переносит исходный Humanoid. Запрещает повторное подключение и mismatch вида, отбрасывает невалидный шаблон. RootCollider остаётся non-colliding/query-only, `RootColliderWeld`/`VisualRootWeld` и skill caster Weld.C0 сохранены. NPC использует visual bounds, Monster — wrapper bounds для ground align как ранее; RootCollider использует visual bounds. Оригинальные MeshPart/texture/rig и ассеты не изменяются.
- `MonsterSpawnerService` и `NpcSpawnerService`: общий порядок create shell → metadata/attributes → attach rig → publish → существующая pose/equipment/hitbox setup → rig ready. `MonsterRigBuilder` теперь только Monster-specific neutral RootBone compatibility; `NpcRigFactory` удалён (NPC authored bones не переподчиняются). Monster AI регистрируется по событию `Game1MnpcRigReady`, без polling и 5s deadline; ожидающие подписки снимаются на ready/destroy/ancestry. NPC Bind по-прежнему вызывается явно после pose. Не допускаем Damageable до готовности сборки. Spawn/respawn policies, death, movement, attack/hitbox algorithm, full presentation и LOD окружения сохранены по коду.
- Старые source-contract тесты и validators перенесены на shared owners; M617/M618 исторические hashes сохранены, исключения только двух намеренно изменённых файлов спавна/рига покрыты M628 contract. `system/verify/mnpc_entity_foundation_m628.lua` исполняет реальные три модуля с минимальным Lua engine double (translation/yaw, дерево Instance, свойства и welding references, не физика Roblox); оба вида, создание без template, metadata, attach wrapped/unwrapped, underground point, unchanged shell transform, collision policy, special Weld, duplicate/mismatched/invalid attach и destroy. Проверки кода также фиксируют оба production entrypoint и прежний combat path.

## Ограничения и следующий шаг

M628 — **не завершён** как весь этап ТЗ. Это общий construction foundation обоих типов, уже используемый production спавнерами. Production всё ещё требует опубликованный template, клонирует FULL при каждом spawn и сохраняет Animator, OBB и прежнюю связь AI с боевой presentation. В runtime ещё нет автономного shell-only движения/AI, detach/rebind с сохранением HP и боевого lifecycle, pose demand или клиентского LOD1/UNLOADED. Не добавлены пустые tracks/no-op presentation для обхода зависимостей. Общий shell может существовать отдельно, но возможность безопасного движения и боя без визуала ещё не проверена в engine. Выигрыш FPS/CPU не заявляется.

Следующая часть этапа M628: развести AI/navigation registration и pose/presentation attachment, сохранив действующие attack timing/death/respawn/equipment; явное владение и освобождение ресурсов при detach/rebind, без изменения OBB. Затем demand-driven server pose и native two-client isolation gate. Тестировать на обоих доменах, не создавать отдельные lifecycle для каждого. Не включать dormancy или strict client LOD до подтверждения readiness. Studio Play / DEV, проверка позиции native welds/animation и обычная игра на телефоне NOT_RUN; стресс-тесты не обязательны по решению владельца.
