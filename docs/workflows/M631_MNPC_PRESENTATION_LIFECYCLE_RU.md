# M631 · MNPC Presentation Lifecycle — M628, шаг 4

База M630. ТЗ: [MNPC](MNPC_LOD_SPEC_RU.md). KBN-0037-T08/A07 остаются открытыми. Цель — общий lifecycle Monster и NPC, не изменение боевого алгоритма.

## Реализовано

- `MnpcVisualRig.Attach` возвращает модель и `MnpcPresentationLifecycle` lease конкретного подключения. Владелец хранит точные ссылки на импортированные wrapper children, VisualRootWeld и зарегистрированную экипировку; без поиска по именам, полного обхода сущности или нового цикла. При Release сначала отключаются Damageable, RigReady и query, затем уничтожаются weld, экипировка и rig. Подготовленные RootCollider, HumanoidRootPart, Humanoid, RootColliderWeld, родитель и игровые атрибуты сущности остаются. Для старого FULL-only пути без подготовленного плана удаляется также его временный query collider/weld. Повторный Release не затрагивает новую сборку. `Attach` к подготовленному shell повторно использует текущий root.
- Оба production спавнера используют один lease. При штатном окончательном удалении спавнеры сначала освобождают доменные AI/pose consumers и `EntityHitboxService`, затем lease и саму сущность. MonsterAgentLifecycle.Unbind добавлен для явной отмены старого AI до уничтожения костей. При внешнем Destroy не требуется повторно уничтожать rig: отдельная ветвь cleanup. Порядок death/sink, respawn и spawn presentation остаётся доменным. Lease не владеет AI, боевыми callback или OBB; их остановка является обязательным условием Release, не делегируется в геометрический модуль.
- NPC equipment context вычисляется до clone и не требует костей/оружия. `WeaponEquipService.ResolveVisual` — общий resolver существующего опубликованного row/template (без clone). `NpcEquipmentService.Resolve` хранит immutable authored hand/slug и ожидаемый weaponType/weaponSet. `Equip` монтирует предметы с прежним socket/rig validation, регистрирует успешные предметы в lease; эффективный weapon context остаётся по первому успешно установленному оружию (right → left → hands), до alignment и AI bind. Контекст до mount не подтверждает боевую готовность. Игровой loadout и stats не изменены; оборудование игрока не менялось.

## Проверка и границы

Lua oracle M628/M630 расширен: Monster/NPC × wrapped/unwrapped release → move → reacquire, сохранение shell, HP и несвязанных объектов, точное освобождение weapon/rig/weld, идемпотентный stale lease, два FULL-only fallback cases. Отдельный oracle M631 исполняет equipment Resolve/Equip с тестовым resolver/mount: пустой loadout, отсутствующий ассет, приоритет рук и fallback при отсутствующем socket. Source contracts проверяют порядок cleanup обоих production спавнеров. Нативный Roblox, реальные joints/AnimationTrack, death/sink и multiplayer не проверены здесь. Тесты не измеряют FPS.

Production всё ещё FULL сразу после создания; новый lease в production используется только при штатном окончательном удалении, не на живых существах по дистанции. Полный безопасный живой pose detach/rebind ещё требует переноса доменных presentation consumers (idle/wander/attack/death, NPC motion/presentation) и отмены/синхронизации их работы без удаления AI/слота. Следующий шаг — общий demand lifecycle и подключение этих consumers с сохранением shell. Не считать строгую per-client изоляцию carrier решённой. Не вводить автономные невидимые боевые цели без readiness gate. A07 NOT_RUN.
