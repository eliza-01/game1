# M634 · MNPC LOD1 preparation (частичный этап authoring)

## Что реализовано

Общий offline generator для Monster и NPC в Asset Manager → LOD Manager → MNPC → Edit → Prepare LOD1. Вход — **уже собранная FULL-модель в проверенной естественной позе с одним общим UV-атласом**, включая оружие, если оно есть. Допустим статический posed FBX или FBX с однозначными embedded actions и явно выбранным кадром. Нативные `.rbxm/.rbxmx` из текущих Monster/NPC animation stores не являются Blender actions; их перенос и автоматическая сборка экипировки из опубликованного FULL пока не реализованы. Не использовать rest/T-pose вместо idle. Никакой обязанности вручную готовить весь каталог на этом промежуточном этапе нет.

- `services/mnpc_lod_prepare.py`: snapshots исходных FBX/atlas во временный каталог, проверка размера и SHA256, единый Blender subprocess (120 s), уменьшение текстуры Pillow с сохранением aspect и alpha, recipe с SHA входов, выбранным frame, triangle cap, исходными счётчиками и размером выходной текстуры. Исходники не меняются. Recipe хранит идентичность входов, но не резервную копию внешнего posed FBX/atlas; оригиналы остаются у автора.
- `prepare_mnpc_lod_fbx.py`: evaluated geometry выбранного кадра, исключение известных технических деталей (rig_carrier, RootPart/HumanoidRootPart/RootCollider, hitbox, retired COL), freeze world transforms без перемещения к bbox origin, один UV на каждой части, UV в [0,1], join, triangulate, decimate до заданного cap, export geometry-only через общий `model_publication.export_model`, повторный импорт и действующий M633 validator. Ограничения: 1–64 частей, 500000 входных треугольников, cap 100–10000 (default 1000), atlas max side 128/256/512/1024 (default 512, без upscale). Качество силуэта, UV-швов, фактическая поза и Roblox root alignment требуют визуальной проверки; указанные числа — стартовые настройки, не benchmark. Выход static lod1 без костей, материалов, анимаций. Произвольные shader/несколько разных атласов не запекаются, на входе нужен один общий atlas; соответствие входа FULL и экипировке подтверждает автор, а не алгоритм.
- POST `/api/lod-manager/mnpc/{kind}/{slug}/prepare`: JSON `posePath`, `texturePath`, `frame`, `targetTriangles`, `textureSize`, `reviewedAssembly=true`, `expectedRevision`, `fullFingerprint`. CAS перед генерацией и перед staging; pending Cloud operation блокирует. Один `MnpcLodResource.stage` и AtlasRegistry, recipe в существующем geometry_json, без миграции. Report M633 от roundtrip принимается только для тех же SHA bytes; ручной stage по-прежнему вызывает независимую Blender инспекцию. Ошибка не заменяет текущую ревизию; уже созданный immutable output может остаться в каталоге. Повтор одинаковых байтов сохраняет ревизию и Cloud IDs. Generate & stage не публикует. Publish остаётся отдельным действием. UI исправляет ID панели busy-state (`lod-mnpc-panel`), сбрасывает подтверждение при смене FULL/входов, показывает исходные и выходные числа.

## Что открыто / следующий этап

Автоматический захват фактического idle и экипировки из опубликованных Roblox templates (не предполагать совпадение Blender и Roblox bind frames); автоматическое формирование общего атласа из отдельных материалов/оружия при необходимости; затем native import/alignment, runtime export, client LOD и строгая изоляция carrier. Production остаётся FULL; M632 pilot OFF; Runtime/AI/OBB/Studio plugin не изменены. M634 — частичная реализация, T08/A07 не закрыты.

## Проверки

SQLite + AtlasRegistry + Pillow с Blender double: оба kind, alpha/aspect, source SHA, revision CAS, stale FULL, отказ, лимиты, HTTP и отсутствие Cloud upload. JS transport double: Generate & stage и refresh. Native Blender test на двух procedural meshes запускается при наличии executable; в диагностической среде Blender и FULL FBX отсутствуют, поэтому нативная генерация и визуальная проверка NOT_RUN. Не считать mocked report доказательством Blender bake.
