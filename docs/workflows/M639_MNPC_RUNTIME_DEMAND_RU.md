# M639 · MNPC Runtime demand / qualified shell-only spawn

Владелец просит закончить Runtime без готовых LOD1. M638 red dummy и все три клиентских стадии сохраняются, authoring pipeline не изменён. M639 завершает код общего серверного demand path для обоих типов, но НЕ объявляет строгую изоляцию native Animator или нативную боевую приёмку выполненными.

## Режим и контракт

- M640: **Options → MNPC LOD → Server rig demand (Monster + NPC) → Save MNPC LOD**. Единственный источник `assets/manifests/options.json` (`mnpcDemand.enabled`) → generated `GameOptionsRegistry` → `GameOptions.MnpcDemandEnabled()` на сервере. Default OFF, прежний Workspace attribute больше не читается; при переходе с M639 один раз включить в Options. После Save выполнить Rojo Sync и перезапустить Play; для опубликованной игры опубликовать Place и запустить новый сервер. При OFF сохраняется визуальный M638, серверная выгрузка отключена. Нативная reattachment/teleport acceptance пока открыта.
- Исторический порог M639–M644 (заменён M645): max(FULL + hysteresis, максимальная дальность зарегистрированного оружия + половина диагонали RootCollider + 8, авторские aggro/attack радиусы) + 48 studs. В Studio/DEV с доступными debug overrides вместо каталожной дальности — MaxAimDistance 420. Освобождение требует ещё +32 studs и непрерывно 5 s без потребности. Консервативная горизонтальная дистанция по всем игрокам. Explicit OFF profile, активный бой/статусы/recovery/return/spawn и GP test исключают освобождение. Это запас, не гарантия готовности при произвольном телепорте/быстром движении.
- Стадии `full / shell / loading / preparing / full`; `Damageable` false и отсутствуют OBB bindings, Animator, rig lease у sleeping shell. Технический root, collider, Humanoid, HP, AI, spawn slot остаются. На первом успешном FULL соответствующего типа/шаблона, после подтверждения готовности и отсутствия потребности, общий owner кэширует квалификацию. Только последующие дальние спавны этого типа допускают initial shell-only; GP и Monster rise-from-ground сохраняют исходную первую визуальную сборку, а неподдержанные/нестабильные rig/loadout остаются FULL. Нет подмены геометрии боя.
- Восстановление через существующий AI scheduler / PlayerSpatialIndex; один общий admission slot, pending candidates сравниваются по расстоянию, повторная проверка актуальности перед стартом. Нет нового Heartbeat, remote, global sort или per-actor timer. Retry 5 s, timeout готовности 15 s после возврата acquire, нативный yielding вызов не отменяется насильно. Клиентская маска/observer не восстанавливают FULL во время `loading/preparing`: сохраняется placeholder до `full` и `Game1MnpcRigReady`. Строгая атомарность нативной репликации не доказана.

## Не закрыто

- Roblox instance streaming / PersistentPerPlayer не дают жёсткого индивидуального порога для репликации native Animator: nonpersistent clients всё ещё получают Atomic model в пределах streaming. Animator.EvaluationThrottled — read-only. M627 уже подтвердил: при реплицированном скелете без визуального меша кости продолжают двигаться, вне Workspace серверный native pose не обновляется. Не удаляем клиентские реплики Animator и не меняем OBB/боевую математику. Если другой игрок активирует FULL, дальний клиент может всё ещё получать и вычислять native skeleton. См. Creator Hub: https://create.roblox.com/docs/reference/engine/classes/Animator и https://create.roblox.com/docs/workspace/streaming . Строгое LOD1 zero native evaluation потребует отдельного доказанного решения; не выдавать visual LOD за этот результат.
- Нативное восстановление рига, движение shell, смена экипировки, спавн/телепорт непосредственно в боевой радиус и два клиента не проверены. До native acceptance не включать demand по умолчанию в production. Во время прогрева возможен красный placeholder и недоступность попаданий: существующие hitbox/pose readiness gates не снимаются. Для disabled demand прежний боевой путь сохранён. A07/T08 остаются открыты; не начинать очередные оптимизации/переписывание боя ради формальной галочки. Пользователь не обязан готовить реальные LOD1 или проводить стресс-тесты.

## Проверки

Lua doubles двух режимов (catalog/debug reach), shared qualification/initial shell, near-first admission, two domain requests, hold, pins, disabled profile, rollback/retry/timeout/cancel, M638 dummy до full readiness; source contracts обеих spawn веток и общего scheduler. Это не Roblox Studio/DEV/mobile native acceptance и не измерение FPS.

### M641 · Диагностика фактических переходов
В LD → MNPC status (Studio/DEV, в том числе без Location manifest) доступен снимок ближайших реплицированных существ: реальная дистанция от корня игрока, desired/actual, причина FULL или отсутствия наблюдения, серверная стадия, профиль и состояние настройки demand. Никакой периодической диагностики. Ошибка отключения клиентского контроллера теперь сохраняется в состоянии для вывода в LD. Нулевой TargetUserId не считается активной целью. GP test и debug reach намеренно сохранены; причину наблюдения FULL на 200 studs нужно подтвердить в нативном Runtime.

### M642 · Custom character spatial root
Нативный снимок M641: FULL/LOD1/OUT 0, WAIT 20; все строки `UNTRACKED | not observed`, `no profile`, дистанция `?`, attack radius 9. Это не отсутствие опубликованного LOD1: наблюдение вообще не запускалось, поскольку клиент искал HumanoidRootPart у custom ControllerManager-персонажа с RootCollider/NavigationRoot. M642 использует существующий CharacterSpatialRoot.Get(player) в MNPC LOD и M626 near-first priority окружения. При отсутствии пригодного корня LD показывает WAIT явно; при появлении/смене корня немедленное наблюдение восстанавливается. Серверные правила demand, включая консервативный запас MaxAimDistance в Studio/DEV, не изменены; `server: full` отдельно от клиентского LOD и сам по себе не является ошибкой. Lua regression с custom avatar без Humanoid/HumanoidRootPart, потерей/возвратом корня и стандартным Humanoid; нативная повторная проверка остаётся открытой.

### M643 · Resource lifecycle verification
LD → MNPC status: M642 визуальные переходы подтверждены пользователем. M643 добавляет counts M/B/A/H (MeshPart/Bone/Animator/CombatHitboxCount) на сервере при стабильном переходе full/shell только в Studio/DEV; отдельно клиентский снимок реплик при нажатии кнопки. H — опубликованный счётчик математических боксов, не количество физических Parts. Снимок сервера не live, не измеряет память или CPU; клиентские количества зависят от streaming. Server counts отражают только наблюдаемые клиентом сущности. Настройки demand не меняются. Историческая проверка до M645 (больше не применяется): отойти горизонтально более 420 + половина диагонали collider + 8 + 48 + 32 studs (обычно >520, либо больше при иных радиусах), дождаться Idle и 5 s без потребности всех игроков; затем вернуться и проверить восстановление H/HP/атаки. Если сущность stream-out, её отсутствие не доказывает shell. Нативная серверная проверка и изоляция Animator всё ещё открыты.

### M644 · Compact MNPC diagnostics
LD → MNPC status: общий снимок сверху (наблюдаемые Monster/NPC, клиентские LOD, серверные стадии, сумма ресурсов реплик и опубликованных H, подтверждённые shell-аудиты), далее группы Monsters и NPC без обрезки по числу строк. Явный вертикальный CanvasSize и touch scrolling; обновление по кнопке, никаких новых обходов/таймеров. Shell audit относится к последнему стабильному переходу, не к live серверному скану; отсутствие shell не считается подтверждением release. Формат снимка содержит численные meshes/bones/animators вместо строки M/B/A. Capture остаётся отдельным видом той же панели. Игровые пороги и жизненный цикл не менялись; нативная UI/ресурсная приёмка остаётся открытой.

### M645 · Общая политика дистанций
По наблюдению владельца M644: клиентские FULL/LOD1/Hidden переключаются, но 20 серверных ригов и 20 клиентских Animator сохраняются. Код M639 удерживал FULL до MaxAimDistance в debug и дополнительных +48/+32. M645 удаляет эти независимые пороги. Клиент и сервер используют `MnpcLodPolicy.Resolve` и общий расчёт текущей дальности конкретного игрока (`AttackRadius` + половина диагонали collider + 8); MaxAimDistance остаётся верхней границей поиска кандидатов/валидации, а не причиной удержания рига. 3D расстояние; при F=100/h=10 серверный FULL выходит на 110, shell запрашивает FULL на 90. Server demand агрегирует игроков: если хотя бы одному нужен FULL, риг сохраняется. Гистерезис сервера относится к общему состоянию рига, а клиента — к его собственному desired LOD; внутри полосы 90–110 возможны различия. Hold 5 s, qualification, readiness, текущие combat/recovery/status/spawn pins и opt-in M640 сохранены. Агро само по себе не радиус визуала; реальное вступление в бой сохраняет/запрашивает риг. Не изменены OBB, урон, AI, авторские дистанции атаки, сеть, UI и генерация LOD1.
Проверка: обычный игрок с коротким оружием отходит за 110 studs и ждёт 5 s вне боя; в LD → MNPC status растёт Shell, уменьшаются client Bones/Animator и server hitboxes, shell audit M0 B0 A0 H0; при возвращении до 90 FULL восстанавливается. Второй игрок рядом или реальная дальняя атака сохраняют риг. Резкая телепортация/смена дальности оружия, нативный rebind и строгая изоляция реплицированного скелета для другого наблюдателя не подтверждены. A07 NOT_RUN.
