# M649 · Hitbox Asset Contract & Geometry Lifetime

> Исторический контракт v1. M651 заменяет формат на v2 и подключает MNPC Studio Edit authoring. Действующий контракт и приёмка: [M651](M651_HITBOX_ASSET_PIPELINE_RU.md).

База: M648 (M645 dump + M646–M648). KBN-0039-T01; T02/T03 остаются открытыми. M648 не объявляется функционально принятым: отдельного результата игровой проверки не поступило. M649 — первый из двух планируемых подходов; нативная миграция может потребовать дополнительного этапа, если выявятся конкретные блокеры.

## Runtime

`EntityHitboxService.Attach` по-прежнему регистрирует те же bone/mesh/head boxes, с тем же алгоритмом M99 и теми же padding, fallback, SAT, headshot, raycast и debug. Записи mesh, bone mapping и scale собираются до чтения геометрии. Сначала проверяется существующий session cache по прежнему ключу, затем версия authoring registry. EditableMesh используется только при промахе обоих кэшей на этапе перехода. Сессионный ключ и его прежняя семантика первого рассчитанного определения сохранены; это не новая политика анимированных хитбоксов.

`HitboxMeshGeometryCache` держит ready-вершины только пока есть пользователи in-flight геометрии. Параллельные Read делят один EditableMesh; Release удаляет данные при уходе последнего владельца. Failed entries сохраняют только маленькую запись ошибки (прежняя permission fallback policy). `preparedVertices` теперь временный локальный массив одной части; после расчёта записи активного binding не содержат геометрии. Ошибка при сборке не оставляет acquired leases. Для разных assembly keys одного mesh возможны повторные чтения до завершения миграции — это компромисс памяти/холодной загрузки, не гарантированное ускорение всех вариантов.

`CombatHitboxDefinitionSource`: session, asset, runtime_migration, root_bounds_fallback. Не менять существующие CombatHitboxMode и CombatTargetGeometry, используемые GP. Нет новых RemoteEvents, фоновых циклов, физических объектов, настройки Options, изменений AI/MNPC или схем БД.

## Контракт v1

Server-only `HitboxAssetRegistry.luau`: `{schemaVersion=1, entries=[{key,signature,definition}]}`. `key` — существующий assembly key (identity, mesh paths/IDs, масштаб, root size, head/parent). `signature` — JSON фиксированного порядка: mesh paths и опубликованные IDs, root-relative frame и scale, выбранное bone mapping для каждого mesh, отсортированные пути и root-relative transformed bone frames, выбранные head/parent paths и общий bone mapping. Frames квантованы с шагом 0.0001; не абсолютные world transforms. Дублирующиеся пути и неопубликованные ID запрещены для persist. Несовпадение означает miss, не приблизительную подстановку; при непустом registry диагностика один раз на key. Точность квантования на реальных ригах и покрытие ключей необходимо проверить в Studio.

Definition содержит `broadRadius`, `sourceVertexCount`, упорядоченный список bodyBoxes и optional headBox. Каждый box — kind, recordIndex для body, boneName для bone/head, локальный центр и размер; вращение локального CFrame по исходному алгоритму identity. Fallback root bounds не экспортируется. Runtime проверяет конечность/размеры, индексы и привязки костей. Неверная схема, неоднозначная запись или несовпадение → migration oracle, никогда не использование непроверенного box. Доверенный registry хранится на сервере, клиент не поставляет данные.

## Авторинг / миграция

`HitboxAssetDefinitions.SetCaptureEnabled(true)` и `ExportCaptured()` доступны только на сервере Studio. Для захвата ранних spawn при необходимости установить Workspace.Game1HitboxCapture=true в Edit до запуска (технический режим для следующего этапа, не инструкция обычной игровой приёмки). Захватывается лишь свежее успешное первое определение, после загрузки геометрии, до повторного использования session cache. Не заменять этот oracle произвольным FBX bounds: Roblox импорт и реальная сборка могут менять координаты и skeleton. Лимит 256 captures на сессию, opt-in, не в опубликованном Runtime. Экспорт возвращает компактный снимок, без вершин. Ошибка захвата не отменяет корректный combat definition.

Control Center `services/hitbox_asset_registry.py`: валидирует формат, нормализует, дедуплицирует по key/signature, не принимает противоречивые записи, атомарно генерирует Luau registry из JSON. CLI для разработки: `python system/control-center/services/hitbox_asset_registry.py <capture.json>`. Это пока НЕ UI Asset Manager и НЕ автоматический экспорт при Publish. Реестр поставляется пустым: реальные данные облачных мешей недоступны в данном дампе. Следующий этап M651 (после M650 near-first fix) — подключить authoring к существующему workflow (переиспользовать Studio bridge/canonical rig assembly), собрать фактические записи Monster/NPC и вариативных персонажей, сравнить OBB/headshot с oracle, проверить coverage, revision invalidation и размер registry (при необходимости разделить на части). Только после полной миграции удалить runtime EditableMesh route, включая существующий permission fallback пересмотреть без изменения боевой механики. Не отключать боевые попадания ради оптимизации. Не объявлять T02/T03/A01/A02 выполненными до нативных доказательств. Никаких специальных действий пользователя на M649, достаточно обычной игры.
