## 1. Область и неизменяемые контракты

MNPC = Monsters + NPC. **Обязательное решение владельца: единая система для всех Monster и NPC, а не две реализации одного принципа.** Общий entity-first lifecycle, navigation shell contract, pose demand/readiness, presentation ownership, LOD policy и runtime budget проектируются с первого шага для обоих доменов. Различия сохраняются в данных и узких адаптерах поведения; никакой зависимости NPC от реализации Monster или наоборот. Это Visual LOD с необходимым разделением жизненного цикла серверной сущности и её представления (entity-first), не замена Adaptive AI LOD M617 и не изменение gameplay, spawn density, дальности агро или урона. Хитбоксы, OBB, headshot, weapon contact, навигацию и native визуальные анимации сохраняем. Не разрабатывать combat_mesh, новые коллизии или собственный evaluator анимаций в рамках этой задачи без отдельного доказанного блокера и согласования. Не распространять на персонажей игроков, training dummy и Studio Preview без отдельного задания. Socket & Door Optimization отложена до проектирования новой системы взаимодействий: текущие сферические зоны неправильно выбирают сокеты между этажами. Overhead UI Pool, Player Attack Sampler, Hitbox Precompute и prewarm остаются в очереди; не реализовывать их целиком в рамках MNPC.

| Стадия | Клиентский визуал | Работа клиента | Сервер |
|---|---|---|---|
| FULL | Текущий полный внешний вид, скелет, оружие, волосы | Анимации, композиция, эффекты и Overhead UI по текущим правилам | Серверное состояние независимо от LOD наблюдателя; боевая поза по необходимости |
| LOD1 | Один цельный статический MeshPart на опубликованный вариант или красный статический dummy | Только следование текущему положению и ориентации root; нет визуального скелета/Animator, sampler, отдельных предметов, эффектов и overhead | Состояние и root сохраняются; pose demand определяется всеми игроками |
| UNLOADED | Ни FULL, ни LOD1 | Нет визуальной анимации, follow, эффектов или overhead; остаётся лишь минимальная запись для обнаружения возвращения | Состояние и root сохраняются; pose demand определяется всеми игроками |

Скольжение LOD1 без анимаций — намеренный компромисс. Не создавать LOD2, billboard impostor, облегчённый скелет и анимационные циклы LOD1. LOD1 генерируется на тип/визуальный вариант, не на каждый spawn; два экземпляра одинакового варианта используют одну геометрию и одну запечённую текстуру. NPC с разной видимой экипировкой/цветом не должны молча отображаться чужим вариантом. Персонаж в FULL выглядит как до рефакторинга.

## 2. Архитектура entity-first (решение после M627)

### 2.1. Что уже подтверждено

До M628 источники: `MonsterSpawnerService`, `MonsterRigBuilder`, `MonsterAgentLifecycle`, `NpcRigFactory` (удалён в M628), `EntityHitboxService`, `HitboxRuntimeFrames`; карта всех связей в [M627 pilot](M627_MNPC_POSE_PILOT_RU.md). До M628 Monster spawn клонировал FULL, определяет bounds по визуалу, затем создаёт navigation root/Humanoid/RootCollider, привязывает visual, регистрирует hitboxes и загружает tracks. `MonsterAgentLifecycle` требует Animator для регистрации и загружает run/combat tracks. NPC имел сходную зависимость rig factory от визуала. Это направление зависимости меняем: сущность владеет своим представлением, не наоборот.

Результат Studio M627 от владельца (28.11.2026, Output 04:09–04:11): plain carrier без MeshParts совпал со skinned reference на четырёх фазах Gremlin (56 bones, 0 stud, max angular error 0,084°) и Guard 02 (74 bones, 0 stud, 0°). Fresh PRIVATE_LOAD вернул tracks, но не дал убедительного движения; MOVE_TO_PRIVATE Gremlin: ~30,04° до переноса, ~0,048° после; NPC: ~153,71° до, 0° после. В клиентском NONE при meshes=0 и NO_OWNED_RIG оба carriers имели по Animator/track, изменяли углы на 25,25°/25,56°, throttled=0. Это подтверждает движение реплицируемого carrier без видимой модели и практически остановившуюся позу в ServerStorage в конкретном эксперименте. Не доказаны CPU cost, полноценные blend/combat clips, per-client exclusion, native streaming behaviour и два одновременно наблюдающих игрока. Persistent fixtures M627 не моделируют обычную стриминговую сцену. Не повторять этот же пилот без нового вопроса.

### 2.2. Целевая схема

```
Spawn / respawn / NPC registration
  -> entity identity + type/variant + home/spawn/HP/life/action state
  -> navigation shell (root, необходимые collider/Humanoid)
  -> AI / movement / pursuit / navigation / combat state
  -> independent presentation consumers:
     SERVER: demand-driven authoritative native pose + existing OBB binding
     CLIENT: per observer FULL rig | LOD1 static mesh | no visual
```

Серверный actor существует с момента спавна до despawn независимо от присутствия визуала, его публикации, streaming, загрузки Animator или наличия игроков. «Точка» — логическая сущность с лёгким navigation shell, а не безусловно бесплатная математическая точка: Humanoid, root, collider, AI и репликация позиции имеют стоимость. Сохраняем существующий способ навигации и физическую модель; не заменяем их самописной кинематикой. `RootCollider` и collision group имеют собственный контракт, отличный от боевых OBB; не объединять и не изменять их ради этой задачи.

### 2.3. Ownership и данные

- Spawn/population владеет identity, spawn generation, home, life/death, HP, respawn, записями AI и навигационным shell. `entityId + spawnGeneration` уникальны; presentation generation меняется независимо. Runtime model с прежними markers/attributes остаётся единственным authoritative actor, пока потребители не мигрированы атомарно. Не регистрировать visual/carrier как отдельный Damageable/AI actor.
- Navigation shell создаётся первым по валидированным метаданным типа: размеры, collider/root offset, ground alignment, hip height, scale, visual-root offset и socket/rig identity. Текущие bounds вычисляются из FULL — извлечь и кэшировать соответствующий контракт один раз на ревизию, а не клонировать FULL на каждого дальнего actor. Проверить эквивалентность на реальном Gremlin и Guard, включая кастеров, rise-from-ground, NPC с экипировкой и тестовые конфигурации. Не вводить guessed bounds или изменённую физику; неподготовленный тип остаётся на прежнем проверенном пути до миграции.
- AI registration принимает готовые entity/root/Humanoid/state, не ждёт Animator. Действия, скорость и тайминг боя отделены от наличия визуального track. Не отключать текущий combat callback или marker простым nil guard: прежде перенести требуемую зависимость на явный readiness/action contract. Сохранить интервалы, randomness/clip selection, hit windows, cancel serial, pursuit, return, navigation ownership, death/loot и respawn. Не переписывать весь AI scheduler.
- Представление не меняет root/HP/home и не сбрасывает текущую фазу действия. Detached assembly и release отменяемы по generation, независимо от population. Server gameplay никогда не зависит от завершения клиентского CDN/preload/mesh. Никаких trust-client hitbox/pose или урона. Клиенту передавать только требуемые для видимого actor данные: identity, variant, root transform, action/phase/speed/start time, life/equipment state при необходимости; использовать существующие attributes/snapshots и native root replication. Не рассылать CFrame каждой кости или OBB всем игрокам, не добавлять per-frame RemoteEvents.

### 2.3.1. Единый фундамент Monster + NPC (обязательно с M628)

- Один общий набор серверных модулей в actor-домене (точные имена после сверки существующих API): entity identity/registry и lifecycle, подготовка metadata и создание navigation shell, регистрация/освобождение владельцев, presentation acquire/release и общий контракт readiness. Один state machine и одна запись на живую сущность. `kind + slug + variant + sourceRevision` различают типы и ресурсы; `entityId + spawnGeneration` различают экземпляры. Не создавать MonsterEntityLifecycle и NpcEntityLifecycle с копиями одних и тех же обязанностей; не делать NPC зависимым от Monster-модуля. Общие модули не импортируют доменные AI/registry; зависимости передаются узкими адаптерами. Не объединять всё в монолитный MNPCService.
- Существующие `MonsterSpawnerService`/population и `NpcSpawnerService`/spawn registry остаются производителями доменных spawn requests; общие операции выполняются shared foundation. Monster/NPC сохраняют свои определения, параметры спавна, AI policies, навыки, экипировку, реплики/взаимодействия там, где они уже реализованы. Различие `kind` не является причиной для второй очереди, отдельного кэша, второго lifecycle или второго общего scheduler. Сохранять существующие markers/attributes через compatibility adapters, не заводить второго Damageable/AI owner.
- Исходные места миграции NPC (до M628): `NpcSpawnerService.spawnOne` клонировал template, вызывал `NpcRigFactory.Create`, `NpcEquipmentService.Equip`, `NpcAnimationRigBinding.Align`, `EntityHitboxService.Attach`, `NpcAnimationService.Create`, затем `NpcCombatAIService.Bind`. `Bind` принимает presentation, а `release` вызывает `presentation.Destroy`, detach hitboxes и destroy entity; callback Dying вызывает `presentation.BeginDeath`. Перенести эти зависимости в общий lifecycle/явный action-readiness contract, сохраняя NPC home reset/refill, death и respawn семантику. Сверить Monster `MonsterRigBuilder`/`MonsterAgentLifecycle` и NPC `NpcRigFactory`/`NpcCombatAIService` параллельно; общий shell строится на проверенных параметрах каждого типа, а не переносе Monster offsets на NPC. Не подставлять пустой Animator или no-op presentation, скрывающие отсутствие требуемого боевого callback.
- Одинаковые переходы spawn → active entity → attach/detach presentation → despawn для обоих видов; общие cancellation/generation, rollback, ownership и cleanup. Независимость от визуала подтверждается и для мирного/стационарного NPC, и для боевого/движущегося NPC, а также для Monster. У NPC взаимодействие и его доступность не должны зависеть от наличия клиентского визуала; значимое локальное взаимодействие запрашивает FULL согласно §3. M645: FULL-потребность хотя бы одного игрока активирует серверный риг и для пассивного NPC; отдельное отключение боевой позы внутри FULL не является частью принятой реализации.
- Общие policy, prototype cache, admission/queue, follow, visual ownership и release на клиенте, общий MNPC authoring/export с фильтрами Monster/NPC вместо двух систем. Доменный adapter предоставляет тип/вариант, метаданные, состояние действия/экипировки и специфические callbacks; не имеет собственной логики переключения LOD. Существующие Adaptive AI/боевые политики не унифицировать искусственно: общая инфраструктура не означает одинаковое поведение существ.
- Допустимы отдельные маленькие коммиты и последовательный opt-in конкретных типов для безопасной миграции, но shared contract проектируется до первой миграции, и M628 не закрывается по одному Monster: оба реальных entrypoint должны использовать общий lifecycle и пройти одинаковые contract/regression checks. Неподготовленный тип может оставаться на явно отмеченном прежнем пути до миграции; это временный fallback, а не постоянная архитектура NPC.

### 2.4. Серверная потребность в боевой позе (не клиентский LOD)

Внутренние состояния pose lifecycle: Dormant → Preparing → Ready → Releasing. Это не дополнительные визуальные LOD. При отсутствии игроков/игровых взаимодействий, которым требуется текущая боевая поза, actor остаётся без живого серверного pose rig/Animator/привязанных OBB; определения OBB в общем кэше сохраняются. Движение и AI продолжаются по существующему Adaptive AI policy, а не по желанию клиента. Скелет, Animator и runtime bindings создаются только при demand. Нельзя отключить их потому, что один наблюдатель перешёл в LOD1.

Demand — объединение потенциально значимых серверных взаимодействий: достижимый атакующий или атакуемый игрок, максимальный допустимый ranged/melee/AOE запрос, projectile/skill in flight, active combat/interaction, специальные сценарии MNPC↔MNPC/скриптового урона (если поддерживаются), death/loot и текущие действия, которые требуют pose. Проверить реальные дальности, включая headshot/raycast, а не только aggro; не вводить искусственный cap дальности ради LOD. Переиспользовать `PlayerSpatialIndex`, `ActorActivityPolicy`, существующий scheduler и индексы боя; игрок и actor движутся, respawn/teleport/late join учитываются. M645: общий порог FULL из профиля MNPC и текущая фактическая дальность каждого игрока (не MaxAimDistance как универсальная дальность). Серверное решение агрегирует наблюдателей по принципу any FULL, с гистерезисом общего состояния рига и hold 5 s; отдельные +48/+32 и отладочный радиус удалены. Реальный бой и существующие gameplay pins не зависят от визуального порога. При резком входе/смене оружия native readiness остаётся открытым критерием. Не создавать отдельный таймер на сущность или глобальный pairwise scan.

При Preparing: заранее запустить bounded acquire authoritative rig и tracks, подготовить/reuse существующие OBB definitions, bind к корректным anchors, восстановить фазу и проверить готовность позы. Для незавершённого запроса атаки authoritative readiness обеспечивается до оценки попадания; подготовка не должна приводить к неуязвимости, пропуску hit window, подмене головы RootCollider или изменению дистанции боя. Если в реальном сценарии этого нельзя гарантировать, конкретный тип остаётся на старом боевом lifecycle (в том числе для дальнего боя); не включать dormancy до решения. Не блокировать общий scheduler ожиданием IO. При Releasing сначала исключить новые/активные pose consumers и инвалидировать callbacks, затем снять OBB bindings и освободить tracks, rig, leases и connections. Сохранять entity и HP. Остановленный, но оставленный у каждого клиента rig не считать выполнением задачи.

### 2.5. Персональный клиентский LOD и репликация (отдельный gate)

Игрок A может нуждаться в FULL и серверной боевой позе, игрок B видеть LOD1, игрок C не видеть ничего. Приоритет — штатные средства Roblox и переиспользование существующих native tracks, без собственной системы семплирования. Проверить независимую структуру shell/pose/presentation, native ModelStreamingMode и реальное поведение стриминга: наличие root/минимального state на LOD1 дистанции при отсутствии ненужного server carrier у этого наблюдателя. StreamingEnabled сам по себе не гарантирует строгий порог индивидуальной репликации; PersistentPerPlayer/Atomic не считать фильтром видимости без доказательства. Не использовать уничтожение реплицируемого server rig на клиенте как гарантированный контракт и не менять глобальные streaming radii ради одного домена. Пилот с двумя клиентами (A near+combat, B far+LOD1, затем смена ролей) должен проверять фактические Instance/Bone/Animator/track counts и движение, не только LocalTransparencyModifier. В пределах видимого диапазона root не должен исчезать только потому, что pose rig выгрузился; если root отсутствует, безопасно убрать visual, не симулировать отсутствующего actor.

Возможна частичная реализация: entity-first + server dormancy уже сокращает работу там, где никто не взаимодействует, но наличие активного реплицируемого carrier на дальнем клиенте остаётся ограничением. Не выдавать эту промежуточную стадию за нулевую анимацию LOD1. Если native isolation не подтверждён, задокументировать конкретную остаточную стоимость/условия, сравнить простые альтернативы на одном типе и согласовать дальнейший путь прежде, чем заменять authoritative pose evaluator. Custom sampling/animation engine, переработка OBB и массовая публикация не входят в M628. Целевой строгий критерий LOD1 сохраняется; A07 открыт до его доказательства или отдельного решения владельца об изменении критерия.

## 3. Дистанционная политика

Настройки по умолчанию для MNPC, возможность индивидуального override по типу: Enabled, FULL distance, Unload distance, hysteresis. Предварительные значения для пилота: 100 / 200 / 10 studs, не утверждённые финальные значения. FULL выбираем достаточно большим, чтобы скольжение не было заметно и значимые взаимодействия отображались в FULL; серверный pose demand использует ту же политику и пороги по §2.4; фактическая дальность экипированного оружия может потребовать FULL вне авторского порога без ограничения урона. Валидировать finite, неотрицательные расстояния, FULL < Unload и неперекрывающиеся зоны hysteresis. Использовать 3D расстояние от игрового персонажа до актуального root/консервативных bounds (единая документированная метрика), а не spawn point; при отсутствии корня персонажа — ожидание, без подмены камерой. При приближении и удалении разные пороги: например переход FULL→LOD1 выше F+h, LOD1→FULL ниже F−h, LOD1→UNLOADED выше U+h, UNLOADED→LOD1 ниже U−h; первый sample без hysteresis; большой скачок сразу разрешает конечную стадию. Не менять политику Location/House M626.

Локальный combat/interaction override FULL для существа, с которым игрок непосредственно взаимодействует: подтверждённая текущая цель/атака на него, атака на игрока, активный NPC interaction. Не считать все агрессивные или атакующие других существ активными для данного игрока. Override не расширяет серверную дальность боя, не принуждает нативный stream-in и не создаёт сущность из отсутствующего root. Использовать существующие достоверные источники локальной цели/состояния и явно проверить их доступность; если источника нет, не вводить глобальную цель или бесконечный pin. Снимать override при завершении, смене цели, смерти, respawn, уходе из взаимодействия. LOD1 не проигрывает death-анимацию: для значимой локальной смерти сохранять FULL до завершения текущего death lifecycle; для дальнего corpse не показывать стоящего «живого» LOD1 — удалить визуал до despawn (или сохранить уже существующий корректный corpse FULL только если это необходимо для текущего gameplay); никаких дополнительных анимированных LOD. Детали death policy проверить на текущих правилах лута/трупов, не изменяя серверный despawn.

## 4. Asset Manager → LOD → MNPC

Третья вкладка рядом с Location Assets и Real Estate. Фильтры All / Monsters / NPC, поиск, компактный список существ из действующих MonsterRegistry/NpcRegistry и фактических authoring store. Для каждой строки: имя/тип/slug/визуальный вариант, FULL source revision, статус LOD1 (missing, staged, published, stale, error), Mesh ID, texture/atlas reference, размеры/пивот, настройки distance с inheritance, действия выбора/генерации, предпросмотра ресурса (только существующим способом, если совместимо), публикации и истории. Не добавлять отдельный менеджер моделей/атласов. Состояние вкладки и фильтра переживает refresh по существующему UI pattern. Пороги MNPC в этом разделе LOD, не дублировать в Options. Единственный переключатель серверной выгрузки — Options → MNPC LOD → Server rig demand (M640). Смена порогов не требует новой публикации mesh. UI должен показывать точный этап ошибки и не отмечать частичную публикацию как готовую.

`system/control-center/static/lod-manager.js` и `services/location_lod_manager.py` — существующий вход LOD; `services/model_lod_common.py` содержит общий inspect/preserve/publish/revision/reuse/distance helpers, domain resources (`location_lod_resource.py`, `house_part_lod_resource.py`) задают ownership. Новый MNPC domain adapter, общий транспорт и shared helpers, не копировать stores. Изучить текущий FBX/Blender/atlas pipeline, Monster/NPC authoring и dependency resolution. Схема и имена полей уточняются по месту, единый writer, версионированный export и fail-closed validation всех consumers. Предусмотреть additive migration с backup и повторным запуском, атомарное сохранение подтверждённых ID и журнал partial publication. Не менять существующие FULL IDs, оригинальные FBX, атласы, анимации и placed instances.

## 5. Подготовка LOD1 и публикация

На вход — актуальная опубликованная конфигурация FULL, все видимые части, масштабы, материалы, волосы и экипировка (если входят в вариант); поза близкая к естественному idle, не T-pose. Запечь деформацию/позу и трансформы, объединить visible geometry, уменьшить полигоны с сохранением силуэта, UV и цвета, запечь совместимые материалы в одну текстуру/atlas. Не включать rig_carrier, невидимые коллайдеры, сокеты, скелет или техническую геометрию. Один MeshPart, без Bones, Animator, Humanoid, скриптов, joint graph. Нативные требования к импорту/лимитам проверить через действующий pipeline; не обещать автоматический bake всех материалов до пилота. При несовместимых материалах/отсутствии source сообщить читаемую ошибку; ручной выбор подготовленного FBX возможен через тот же staged validator, не отдельный runtime путь. До публикации показать triangle count/размер/позу; exact target decimation не закреплять без проверки качества. Зафиксировать root-relative origin, scale и alignment по FULL; не вычислять каждый раз от T-pose bbox. Mesh/texture IDs принадлежат опубликованной ревизии, с fingerprint входов (включая экипировку, atlas, pose recipe). Изменение FULL приводит к stale, не автоматической замене или скрытой перепубликации. Сохранять source и историю; reuse только после проверки совпадения визуального контракта. Не создавать один cloud asset на spawn.

## 6. Runtime: разделение ответственности

- Discovery/lifecycle: один общий MNPC adapter для Monster/NPC, domain-specific identity/state selectors; использовать существующие runtime markers (`Game1NpcRuntime`, `Game1MonsterRuntime`), entity identity + spawn/visual generation. Initial discovery один раз; event-driven register/unregister/stream-in/out; streaming absence не означает server death. Поздние attributes/root/prototype учитываются. Не сканировать весь Workspace каждый кадр.
- Distance/candidates: динамические сущности нельзя помещать в immutable StaticPlacementIndex. Переиспользовать подход локальной пространственной выборки, проверить native spatial query по существующим collider/root и доступность на клиенте; если потребуется динамический индекс, обновлять при движении с консервативными bounds, без нового Part на запись. Общий bounded observation, например 0,25 s в существующем scheduler; движение самого существа инвалидирует threshold clearance. Отдельно учитывать прежние actual/pending/forced и удалять их, даже если они вне выборки. Не запускать таймер на сущность.
- Policy/queue: pure Resolve; одна pending entry на identity/generation; desired отдельно от actual; очередь M620 и near-first M626 с общей arbitration/work budget там, где контракт совместим. Существующая очередь окружения не должна голодать из-за движущихся NPC, а атакующий сосед не должен ждать дальний дом; ограниченное priority class и fairness, без бесконечного блокирования missing. Общий coordinator/adapters предпочтительнее параллельных полных schedulers. Учесть, что LocationWorldStreamer зависит от manifest: MNPC должен работать и в Studio Play/Place без Runtime manifest, без изменения поведения Authoring Preview. Вынести общий runtime orchestration при необходимости, не создавать второй независимый суммарный бюджет.
- Resource/cache: использовать LodPrototypeCache с доменным validator, generation-aware immutable metadata и readiness events; не переиспользовать Location template key для MNPC. Переиспользовать bounded async admission, если подходящая API; отсутствие template не блокирует весь мир. Публикация visual только через owner commit, с актуальными root/identity/scale/desired/generation checks. Новая геометрия строится detached, старая остаётся до готовности. Не считать MeshPart созданным равным GPU/CDN ready; проверить видимый pop и по возможности общий bounded preload только для нужного кандидата, без загрузки всего каталога.
- Assembly: использовать LodAssemblyJob/LodRuntimeWork либо минимальное расширение их общего job interface. FULL может содержать bones и constraints, поэтому не пихать rig в static mesh job ценой потери структуры. Учесть реальную стоимость staging/commit/retire, ограничить active jobs/async slots и pending/retired bundles. Сохранить общую нагрузку M622/M626 (текущие 12 build, 8 cleanup, 132 commit units, 16 lookup per category, не CPU deadline); новые лимиты только после обоснования. Никаких монолитных Clone-обходов на каждом кадре. Нативный Clone большого рига неделим — измерять отдельно, не скрывать под счётчиком одного дешёвого unit.
- Motion: LOD1 следует за текущим реплицируемым root CFrame с сохранённым offset/scale; предпочтительно существующий native binding, если он безопасен для network ownership и physics, иначе общий обновитель только активных LOD1 с плавным следованием. Меш локальный, без коллизий, query/touch, не меняет серверную физику и не перехватывает raycast. Никаких per-actor RenderStepped connections; UNLOADED не участвует в follow. Не экстраполировать через телепорт или утерю root.
- Presentation lifecycle: FULL consumer bind после готовности актуального rig; при commit в LOD1/UNLOADED — release sampler lease, disconnect composition, native visual playback/rig disposal, effects/weapon/hair/overhead cleanup. При возврате FULL получить текущий snapshot/phase/health/death/equipment, не воспроизводить устаревшие события; без T-pose flash и с корректной отменой async acquire. Не менять M609 RigidConstraint; не возвращать follower. Проверить `ActorSamplerPool`, Monster/NPC locomotion controllers, `NpcWeaponVisibilityController`, `MonsterHomeRecallVisuals`, `OverheadHealthController`, `NpcOverheadController`, `StatusEffectVisuals`, combat feedback/arrow visual, target selection, HUD/portraits, client bootstrap и server lifecycle. Удаление локального визуала не должно удалить authoritative actor. UI вне FULL отключён, но состояние HP/GP/name и серверная логика не сбрасываются. Не реализовывать отдельный глобальный UI pool в этой задаче.

## 7. Fallback и safety

Миграция по одному типу под opt-in; старый путь целиком остаётся для неподготовленных типов. Нельзя переключать live actor между двумя gameplay owners: rollback через безопасный lifecycle boundary (например следующий spawn), с явным состоянием и без дублей; не сбрасывать HP в действующем бою. Успешное удаление визуала не равно освобождению native pose carrier.

M638–M645: опубликованный LOD1 не является условием включения визуальных переходов. Для отсутствующего/невалидного/stale LOD1 в стадии LOD1 показывать красный локальный dummy без скелета, анимаций и физического взаимодействия; за hide — UNLOADED. При наличии готового проверенного LOD1 подменить dummy. Серверный opt-in независим и по умолчанию выключен; неподдержанные серверные конфигурации сохраняют прежний безопасный FULL-путь. При отказе загрузки не заменять действующий визуал пустотой; bounded retry, generation invalidation и понятное предупреждение. Пропажа root — убрать owned visual и подписки сразу; respawn/stream-in не использовать старую generation. Kill switch MNPC выключает feature безопасно: восстановление действующего FULL lifecycle, освобождение staging/cache/queue/connections; не поддерживать две конкурирующие системы для одной записи. После завершённой миграции удалить заменённый legacy, не удалить общий fallback для неподготовленного ассета.
