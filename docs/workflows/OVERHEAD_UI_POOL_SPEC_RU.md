**Актуализация M648:** разработка обоих этапов завершена, владелец подтвердил обычную функциональную приёмку («все нормально»); T05 выполнена, полная ресурсная A05/матрица устройств NOT_RUN. Исходное ТЗ ниже сохраняется как контракт. См. `M647_OVERHEAD_INTEGRATION_RU.md`.

**Проект:** Eyesland / game1

**Kanban:** KBN-0037-T05 / A05.
**Статус:** исходное согласованное ТЗ до реализации. Текущая поставка и проверки: M646_OVERHEAD_UI_POOL_RU.md.
**План:** два содержательных подхода, третий только при конкретной выявленной необходимости. Номера M646/M647 предварительно закреплены за этими подходами.

## 1. Цель и подтверждённая проблема

Минимизировать клиентские UI Instances, подписки, анимации HP и работу с интерфейсами существ, которые игрок не видит или которым не положено показывать интерфейс. Приоритет — стабильность слабого телефона, а не искусственная экономия любой ценой. Визуал, реакция на бой, управление и правила видимости сохраняются.

Проверка исходников M645:

- `src/client/combat/OverheadHealthController.luau`: после появления атрибутов Monster и RootCollider создаёт `HealthBarView` независимо от расстояния/фокуса/LOD. Два разных понятия (зарегистрированная цель и созданный GUI) объединены в `monsterViews`; поиск цели лучом тоже использует эту таблицу.
- `src/client/combat/NpcOverheadController.luau`: аналогичное eager-создание view; отдельный цикл Heartbeat 0,1 s; ожидание GUI включает отдельную `player.ChildAdded` подписку на каждый ожидающий NPC.
- Оба контроллера уже проверяют `MnpcLocalVisibility.Full(model)` (локальный `Game1MnpcLocalLod`), но только скрывают созданный UI. Переход на LOD1/UNLOADED не освобождает view и его связи с моделью. Серверная выгрузка рига не уничтожает саму entity.
- `HealthBarView.Create`: создаёт BillboardGui и дерево UI; удерживает ссылку на конкретную модель, anchor, набор attribute-сигналов и подписку Language; HP/MaxHP уже обновляются событийно. При смене привязки нужно гарантировать освобождение всех этих ресурсов, включая Tween. Пересчёт visualTopOffset обходит потомков модели; его нельзя переносить в регулярный тик.
- `MonsterIconView.Create`: Gameplay Test-портрет строится из Frame по пиксельным сериям `MonsterIconAtlas`. Это особый, более тяжёлый вид представления, а не обязательный портрет обычного монстра. Нельзя умножать этот расход заранее или ломать GP.
- `MnpcNavigationShell` создаёт CanQuery=false корни; `MnpcVisualRig` включает query у готового коллайдера, `MnpcPresentationLifecycle` выключает при освобождении. Поэтому нельзя просто использовать native overlap всех shell как полную замену реестра. Нельзя менять физические флаги ради UI.

Вывод статического анализа: ленивое выделение и ограниченный общий пул обоснованы. Фактическое улучшение FPS, памяти и CPU пока не измерено. Не заявлять его как доказанный результат.

## 2. Границы задачи

В задаче: Monster/NPC overhead, текущий собственный overhead игрока как потребитель общего view API, общий клиентский жизненный цикл UI. Отдельные экранные HUD и GP-функции сохранить. Не добавлять UI над другими игроками, если его не было.

Вне задачи: изменения MNPC LOD/Demand/AI, коллизий, хитбоксов, репликации, боевых атрибутов, дизайна интерфейса, правил отображения, баланса, сокетов и анимаций персонажей. Не добавлять новые сетевые события, манифесты, таблицы БД или настройки Options без конкретной необходимости. Настройки Desktop/Mobile и существующий debug preview остаются авторитетными источниками стиля и радиусов. Не строить глобальную систему pooling всех GUI игры.

## 3. Архитектурный контракт

Один общий фундамент для Monster и NPC, не один монолит. Имена ниже рабочие; перед изменением проверить коллизии с реальными именами и принятые в проекте соглашения.

| Обязанность | Компонент | Контракт |
|---|---|---|
| Реестр готовности сущностей | `MnpcOverheadRegistry` | Регистрация Model и kind, актуального RootCollider, принадлежности папке, readiness; события добавления, изменения anchor/LOD и удаления. Не владеет GUI. |
| Решение о видимости | `OverheadVisibilityPolicy` + небольшие Monster/NPC policies | Из входного снимка вычисляет name/HP/portrait и eligibility; не создаёт Instances, не владеет подписками и не пишет игровые атрибуты. |
| Владелец представлений | `OverheadViewPool` | Единственный общий пул для MNPC на клиенте; Acquire/Release/Destroy; контролирует lease, свободный запас и очистку. Не решает кого показывать. |
| Представление | существующий `HealthBarView`, `MonsterIconView` | Создаёт переиспользуемое дерево, Bind/Unbind, ApplyStyle/SetSegments/SetIcon; локальные подписки только пока привязано. Не знает дистанционных правил. |
| Координация | общий `MnpcOverheadController` | Один цикл выборки кандидатов и применения policies; получает события реестра и настроек, назначает и освобождает views. Не содержит реализации UI, правил боя, генерации портретов. |
| Собственный overhead | существующий `OverheadHealthController` (или выделенный небольшой self-адаптер) | Сохраняет собственную видимость и респавн; использует тот же view API, выделенный view вне MNPC-пула. |

`NpcOverheadController` и Monster-часть `OverheadHealthController` не оставлять как параллельные владельцы UI или таймеров. При миграции заменить реальные entrypoints в `src/client/init.client.luau` и обновить все ссылки. Старые модули удалять, если больше нет потребителей, а не сохранять мёртвые wrappers для текстовых тестов.

### 3.1 Жизненный цикл

1. Model появляется в `Workspace.Monsters` / `Workspace.NPCs`; регистрируется лёгкая запись без BillboardGui и без подписок view на HP/стиль/язык.
2. При появлении валидных runtime-атрибутов, `LifeState`, slug, RootCollider запись становится готовой. События могут прийти в любом порядке. Нет ожидания с таймаутом, polling-потока на модель или отдельного listener PlayerGui на каждую модель.
3. Если FULL, Alive, anchor актуален и текущая политика требует хотя бы один видимый сегмент, запросить view. Eligibility вычисляется **до** Acquire, включая настройки disabled и исключения GP. `nil` локального LOD сохраняет действующий compatibility-контракт `MnpcLocalVisibility.Full` для незарегистрированных/отключённых LOD, но не заменяет проверку готовности anchor/модели. Не создавать UI для shell/перехода с неготовым FULL.
4. Bind применяет все актуальные данные модели и настройки, затем показывает view. Первоначальный HP и цвет устанавливаются без Tween со старого значения. Один view принадлежит ровно одной сущности, одна сущность имеет не более одного view.
5. При исчезновении eligibility (в том числе LOD1/UNLOADED, смерть, stream-out или замена anchor) скрыть view, отменить Tween, отсоединить все связи с прежней моделью, сбросить данные, Adornee и вернуть в пул либо уничтожить. Событие LOD/death/removal не ждёт очередного обычного тика.
6. При возвращении FULL и eligibility вновь Bind из текущих атрибутов, без сохранённых значений прошлого владельца. Не ждать респавна, не создавать копии.
7. При смене PlayerGui, папки существ, Character или остановке контроллера корректно освободить/перепривязать все соответствующие ресурсы. Start идемпотентен; Stop отключает общие подписки и очищает пул. Устаревшие callback не могут менять новый lease (generation/token или эквивалентный контракт).

### 3.2 Пул и ограничения

- Ленивый, общий, без стартового прогрева. Свободные views не находятся на видимом HUD, не имеют Adornee и не удерживают model, HP connections, Tween, портрет владельца или closures со старым владельцем.
- Предварительный внутренний лимит свободных: 8 простых MNPC views, idle TTL 5 s. Уточнить по проверкам; это ограничение кэша, не оценка миллисекунд. Освобождённые GP-портреты уничтожать или использовать ограниченный переиспользуемый canvas без остаточных данных; не сохранять произвольные деревья пиксельных Frame в idle-пуле. Не заводить отдельный Monster/NPC pool.
- Активные views ограничены фактическим количеством eligible существ. Не вводить произвольный hard cap, из-за которого обязательный HP пропадает при массовом бою или GP. Если создание на холодном старте требует распределения, в общем координаторе ограничить новые allocations за тик (предложение: 4) с приоритетом текущей цели/атакующих и ближайших, без задержки использования уже свободных views. Критическое отображение HP имеет приоритет перед косметикой, без starvation. Отмена заявок при изменении eligibility. Не добавлять независимые таймеры/Heartbeat.
- При повторных переходах не пересоздавать базовое дерево GUI, пока есть свободный совместимый экземпляр. Не перебирать его потомков каждый кадр. Очистка в существующем тике или при событии. Сброс полного состояния (цвет, HP, текст, level, агрессия, icon, stats, offsets, MaxDistance, style, Active/passthrough, Enabled/Visible, tween, parent, Adornee).
- `HealthBarView` должен отделить creation от binding. Удержание ссылок на старую модель через closures недопустимо. HP/MaxHP event subscriptions принадлежат lease. Style/Language — общие уведомления владельца или отключаемая подписка только на активный lease, без listener на каждый idle view. Отмена Tween до смены binding и игнорирование stale событий. При unchanged HP не запускать повторный Tween.

### 3.3 Выбор кандидатов и бюджет обновления

Сохранить текущую частоту проверки динамической видимости 0,1 s одним общим тиком для MNPC. Использовать `CharacterSpatialRoot.Get(player)` для позиции игрока, не предполагать HumanoidRootPart; совместимость custom/обычных персонажей проверяется. Не вычислять дистанцию для LOD1/UNLOADED без причины; активные/недавно активные leases обрабатывать для немедленной очистки. Событийно инвалидировать readiness, локальный LOD, смену anchor, GUI и профиль; не реагировать созданием UI на каждое изменение HP далёкой сущности.

В первой реализации допускается единый недорогой обход лёгкого FULL-ready реестра вместо двух обходов UI-деревьев. Не обещать отсутствие любых глобальных обходов, если они остаются. Если число FULL-кандидатов оправдывает native broadphase — переиспользовать `NativePartSpatialIndex` только на queryable FULL RootCollider и проверять точную 3D-дистанцию, возвращать ранее активные leases для освобождения, сохранять GP same-zone portrait без ограничения ordinary radius. Обязательно проверить изменение CanQuery, фильтры CollisionGroup и streaming; не пропускать допустимые цели. Не создавать новый универсальный динамический индекс ради этой задачи и не копировать серверный индекс в клиент. Выбор broadphase задокументировать и обосновать; по умолчанию не расширять scope.

Ретикл: один существующий aim ray с `CameraController.GetAimRay()` и текущим exclude своего персонажа, player-centered radius + camera margin 64. Тот же учёт препятствий, autoaim lock. Поиск попадания по **зарегистрированной модели** (не по наличию view), иначе первый HP никогда не сможет появиться. Не заменять авторизованную боевую цель ближайшей сущностью. Не менять CameraController/AttackController без необходимости.

## 5. Сквозная совместимость — обязательный gate

Для каждого изменения API/межмодульного контракта сначала составить карту производителей/потребителей и актуализировать всех в одном патче. Не оставлять временные несовместимые состояния между поставляемыми этапами. Если меняется схема данных/манифест — проверить полную цепочку authoring → storage → validation → generated registry → Runtime → UI и обратные операции. В этой задаче по умолчанию схема не меняется.

Минимальная карта:

- `src/client/init.client.luau` — единственная регистрация MNPC coordinator и self overhead; порядок с LOD, Camera, Language и PlayerGui, повторный Start/Stop.
- `MnpcLodController`, `MnpcLocalVisibility`, `MnpcDemandLifecycle`, `MnpcPresentationLifecycle`, `MnpcNavigationShell`, `MnpcVisualRig` — производители локальной стадии, readiness и anchor lifetime. Переиспользовать фактическую стадию, не дублировать пороги. Не вносить изменений ради UI, если контракт достаточен.
- `MonsterSpawnerService`/`MonsterInitialAttributes`/AI/home recall/death, NPC spawn/AI/combat/respawn — производители HP, MaxHP, LifeState, Level, названий, агрессии и target. Проверить delayed replication и прежние тестовые атрибуты; серверную authority не менять.
- `CameraController` (GetAimRay/AutoAimTarget), `CharacterSpatialRoot`, управление PC/mobile и input passthrough — потребители UI/видимости; не менять луч и управление.
- `HealthUiSettings`, `GameOptions.NpcOverheadSettings`, `GameOptions.HealthUiSettings`, options_store/generated registry и `HealthUiDebugController`, `PlayerHealthHudController` — сохранить profiles, preview и сохранение; не изменять schema без нужды.
- `HealthBarView`, `MonsterIconView`, `MonsterIconAtlas`, `NpcDisplayNameFormatter`, `LanguageState` — потребители binding/стиля/локализации и GP.
- Проверить все `rg` references на удалённые/изменённые модули и методы, включая Studio/debug/GP и тесты. Не поддерживать два пути в Runtime и не маскировать несовместимость dummy-обработчиками.

Любая ошибка readiness — ожидаемое состояние до прихода зависимостей, а не повод молча пропускать навсегда. Invalid contract, неверный тип, ошибка создания/Bind или потеря владения — явная диагностика с причиной, без спама, гарантированная очистка частично созданных объектов, безопасный повтор по событию или ограниченному retry. Не использовать blanket `pcall` с игнорированием ошибки. Не допускать утечки подписок при исключении. Никаких новых per-actor frame loops.

## 6. Два подхода к реализации

### M646 · Общий Overhead lifecycle и pool

В одном целостном патче: извлечь и проверить политики видимости, разделить регистрацию/eligibility и view ownership, переделать HealthBarView на безопасный rebind, подключить общий пул для обоих типов и общий цикл, мигрировать self overhead. Сохранить GP, локализацию, настройки и управление. Удалить прежние дублирующие владельцы. Не сдавать библиотеку, не подключённую к реальным entrypoints.

Проверка подхода: чистый apply/reverse-check, Lua lifecycle/oracle, профильные регрессии и verify; Studio Play smoke обоих типов (обычная игра), опубликовать в DEV и проверить короткий Runtime smoke. Нативные результаты, если недоступны исполнителю, честно NOT_RUN; совместимость кода и фактическая игровая совместимость отмечаются отдельно. Исправлять найденные блокеры до приёмки.

### M647 · Интеграция, ресурсная проверка и завершение

По результатам M646 устранить конкретные регрессии, проверить GUI reset, streaming, смену языка/стиля, GP icon-only и быстрые переходы LOD. При необходимости скорректировать бюджет и дорогой GP portrait creation; не добавлять новые подсистемы без подтверждённого дефекта. В существующей DEV-панели добавить только при необходимости компактный счётчик: Active / Idle / Created / Reused (и active subscriptions при ресурсной проверке). Без отдельного profiler, постоянных дорогих scans и новых remote. Можно объединить с M646, если интеграция подтверждена и патч остаётся обозримым. Не создавать M648 ради дробления.

В конце синхронно обновить `docs/README Read First!.md`, README, AGENTS.md, Current Project Spec, Current Architecture, Mechanics, соответствующий workflow и Kanban KBN-0037 (T05/A05, история/revision/hash/acceptance). Документировать реальные тесты и оставшиеся ограничения. Согласованные следующие приоритеты не менять молча; после Overhead — Character Creation Prewarm, Hitbox Precompute, Priority Animation Prewarm, Player Attack Sampler (последовательность из обсуждения после M645; сверить/зафиксировать в актуальном Kanban при реализации). Socket & Door, stress tests, общий Profiler и Incremental Studio Preview остаются отложенными.

## 7. Проверки и критерии приёмки

Автоматические — проверять реальные используемые Luau-модули, а не только совпадение строк. Mock/модель не выдавать за нативную Studio. Текстовые guardrails актуализировать только после проверки сохранения поведенческого контракта; не удалять тесты ради зелёной статистики.

- Таблица решений M645 vs новая policy: ordinary Monster focus/lock/aggro/return/death/preview/disabled; NPC отдельные радиусы и HP; GP owner/group/zone/icon-only; FULL/LOD1/UNLOADED; self.
- Реальный Lua pool lifecycle: Acquire/Release/rebind двух разных типов, initial fill, отмена tween, generation/stale event, double release, cleanup partial failure, idle cap/TTL, reuse after moving, Stop/Start, bounded pending work.

## 8. Правила поставки

Архитектура MMO: обязанности разделены, переиспользуемы, модули не зависят от конкретного типа существа там, где это не необходимо. Не создавать монолиты, дублирование, легаси и необоснованные абстракции. Предложения оцениваются критически по пользе, стоимости и риску. Согласованный scope не расширять на смежные системы без основания.

Каждый патч содержит полностью согласованные producer/consumer изменения, список затронутых контрактов, фактически выполненные проверки и открытые ограничения. Поставлять Git patch + один PowerShell-блок установки: `git apply --check`, остановка Rojo перед изменением файлов, применение, профильные проверки, plugin install только при изменении плагина, restart Control Center по необходимости и фоновый запуск `sync.ps1` без блокировки консоли. Учитывать, что остановка всех процессов rojo может затронуть другие проекты (существующий согласованный workflow). Никаких требований ручного редактирования кода/консольных команд Roblox для обычной проверки.
