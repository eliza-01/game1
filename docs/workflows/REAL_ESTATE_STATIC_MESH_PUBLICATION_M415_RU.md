# M415 · Публикация отдельного статического MeshPart дома

- Исходный полный FBX дома и независимый `rig_carrier` продолжают требовать один канонический `house_armature`: он владеет сокетами и исходным pivot.
- Отдельная FBX-ревизия **одного визуального MeshPart** без скелета публикуется как статическая модель. Публикация не создаёт фиктивных костей или нового `rig_carrier`.
- При замене статической части сохраняется её зарегистрированное авторское положение (`authoredPlacement`, версия 3) относительно исходного pivot дома. Для сохранённых до M415 частей без этого поля оно восстанавливается из проверенного оригинального полного FBX (SHA должен совпасть). Если подтверждение невозможно — публикация останавливается **до загрузки**.
- На Studio Sync компилятор загружает общий `rig_carrier`, проверяет все визуальные Model Asset ID и полный Bone manifest каждой части. Только независимые статические FBX получают восстановление положения по `authoredPlacement`; остальные части сохраняют общий pivot. Далее используется существующий механизм обновления управляемых домов на Workspace.
- Studio Sync доступен только после проверки `publishedSha256` каждой части на совпадение с `rigPublicationHashes`. `Sync entire house` дополнительно требует актуальных атласов всех частей. Успешное завершение задания публикации само по себе не подтверждает готовность Studio Sync.
- История ID, атласы, Plot, двери, коллизии, сокеты и LOD не мигрируют и не очищаются.

**Граница тестирования:** в диагностическом архиве нет самих FBX и Roblox Studio. Проверены Python/JS/Luau-контракты и подготовка статического FBX с имитацией Blender; реальный импорт Roblox, позиционирование и Undo требуют Studio Play на резервной копии Place.
