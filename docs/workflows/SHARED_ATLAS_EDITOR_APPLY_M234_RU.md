# M234 · Asset Manager — единый редактор Atlas, Apply Changes, Studio Sync

## Причина переработки

M232/M233 оставляли в Location Assets несколько взаимоисключающих способов сохранения FBX, physics и atlas. В Real Estate существовал параллельный модальный интерфейс Atlas; сообщения об ошибке Studio Sync терялись во временном уведомлении. Перенос старой формы регистрации в Edit не является допустимой архитектурой.

## Границы и владелец данных

- **`services/texture_atlas_registry.py`** — единый источник истины для atlas key, опубликованных вариантов, Image ID, одной активной привязки на потребителя и дополнительных подключённых вариантов. Таблица `texture_atlas_consumer_options` добавляется миграцией с резервной копией SQLite; существующие bindings и публикации не переписываются.
- **`services/atlas_source_review.py`** — только чтение/превью выбранной PNG/JPEG/WebP, SHA-256 и повторная проверка перед явной публикацией; вспомогательное создание превью используется также Characters. Превью не мутирует Registry. Исходник PNG/JPEG/WebP нормализуется по действующим правилам Registry в каноническое имя `<atlas_key>_<width>x<height>_atlas.png` (либо `.jpg` для JPEG), с проверкой фактических размеров. Встроенный WebP в файле с суффиксом `.png` преобразуется во временный настоящий PNG; исходный файл не изменяется.
- **`static/asset-atlas-editor.js`** — единый интерфейс для Location Assets и Real Estate, сам не знает про FBX/геометрию/Studio и принимает только `consumerType`, `slug`, `part`, revision и refresh callbacks.
- **`location-asset-workflow.js` / `real-estate-mesh-workflow.js`** — тонкие доменные редакторы. Публикация Model не обращается к публикации Atlas; смена Atlas никогда не инициирует Sync.
- **`api/write_world.py`** — тонкие POST-ручки; доменные `select_atlas()` продолжают проверять существование потребителя и оптимистическую ревизию. History/audit импортируется через общий write-dispatch.

## HTTP-контракты

- `POST /api/texture-atlases/consumer-choice` `{consumerType,slug,part?,action:'attach'|'select',variantId,expectedRevision?}`: `attach` сохраняет вариант в доступные точки, не меняя активный Image ID; `select` атомарно меняет единственный активный binding, только для зарегистрированного Location Asset или визуальной части дома. Оба метода не трогают Roblox Studio.
- `POST /api/texture-atlases/preview-source` `{sourcePath}`: возвращает `oldPreview`, `newPreview` (локальные PNG data URI 256 px), зарегистрированный вариант, версию Image ID, SHA-256, признак совпадения/необходимого согласия. Ни записи, ни Open Cloud upload.
- `POST /api/texture-atlases/publish-reviewed` `{sourcePath,sha256,expectedVariantId,expectedPublishedId,approveReplacement}`: повторно проверяет файл и состояние версии; при совпадении ключа/разрешения и изменившихся байтах опубликованного изображения требует явное `approveReplacement=true`. Сохраняет новый источник и публикует через общий Atlas Registry, не отправляя Studio-команды. Операции с неопределённым Open Cloud результатом продолжают блокироваться Registry. При сбое экспорта после **успешной** публикации возвращается успешный результат с `exportWarnings`, без предложения слепо повторять upload. Аудит проверяется до мутации и предупреждает о сбое импорта после неё.

Семейство с несколькими вариантами (например 512/1024/2048) автоматически отображается рядом с активным вариантом для старых потребителей. Новые внешние варианты подключаются только явным нажатием; подключение не является выбором. Состояние подключённых вариантов переживает перезапуск Host Agent.

## UX и пользовательский сценарий

**Location Assets → Edit → Model · FBX** показывает зарегистрированный файл, анализ MeshPart/скелета и настройки physics. Если изменены только свойства мешей — зелёная пульсирующая `Apply Changes`, без Open Cloud. Если выбран новый FBX либо ещё нет актуальной публикации — `Publish and Apply`: сохраняет изменения, затем вызывает исключительно `publish-model`, подтверждающий неизменность Atlas ID. Отдельных `Save mesh settings`, `Save FBX revision + physics` и `Republish Model · new ID` нет.

**Texture · atlas**, в обоих доменах: текущий опубликованный вариант и Image ID; цветные точки привязанных вариантов; `Connect existing atlas` с поиском всего опубликованного каталога; `Upload new atlas` с чтением PNG/JPEG/WebP и предпросмотром нового файла. Если имя/размер уже есть и изображение изменилось, показываются old→new превью и чекбокс явного подтверждения **общей** перепубликации. После подтверждения изображение сохраняется в проекте автоматически; отдельной `Save image source` нет. Привязка к текущему потребителю меняется только явно. Другие потребители общего атласа получат pending Sync.

**В нижней части модалки, на любой вкладке** находится `Sync Model + Atlas · Studio`: отдельное действие, синхронизирующее только выбранный slug (Real Estate — конкретную часть). Отказ Studio Bridge отображается **в самом окне**, а не как `see notification`.

## Безопасность и ограничения

- В M234 **нет изменений Studio-плагина, Luau, размещённых моделей, физики, CFrame, Pivot, MeshId, published Model/Image IDs или содержимого существующего Place** при установке.
- Shared Atlas Registry допускает один active binding на потребителя. `attach` и `select` не запускают Open Cloud. При перепубликации **существующего** варианта Image ID меняется для **всех** его потребителей; требуется явное подтверждение и затем адресный Studio Sync.
- При сетевой неопределённости или проверочной ошибке предыдущий опубликованный Image ID не удаляется. Не нажимать повторно «Publish» при неразрешённой pending operation; использовать существующий recovery.
- Предпросмотр использует те же правила canonical filename / проверки native image format, что и `AtlasRegistry.adopt_file` (M213); файлы WebP конвертируются во временный PNG до записи. Неподдерживаемые/повреждённые источники отклоняются до изменения Registry.
- Реальная публикация Roblox, выбор файла в OS picker и Studio Sync должны пройти smoke-тест на копии Place. Python/Node unit tests не подтверждают их фактическое выполнение в Studio.

## Smoke сценарий

1. Открыть два Location Assets и один Real Estate mesh с общим опубликованным атласом. Подключить чужой вариант к одному потребителю, проверить, что текущий Image ID других объектов не изменился.
2. Переключить точку — меняется только active binding, Place не изменяется. Повторно открыть UI — выбранный вариант и остальные точки сохранены.
3. Выбрать локальный файл с тем же canonical filename, но изменёнными пикселями; сравнить old/new preview, отменить (нет изменений в DB/Roblox), затем подтвердить. Проверить обновлённую историю и pending Sync всех потребителей.
4. Location Asset: поменять только `No Collide`/`DoubleSided`, нажать `Apply Changes` — Model ID неизменен. Выбрать новый FBX, проверить `Publish and Apply` и неизменность Image ID.
5. Имитировать сбой Studio Bridge: модальное окно отображает текст отказа. Кнопка Sync доступна независимо от вкладки.

Применение: Git-патч **поверх M233**, перезапуск Host Agent и `Ctrl+F5` в Asset Manager; Studio-плагин не переустанавливается.
